# pi 本机文件工具

Status: ready-for-agent

## Problem Statement

用户已经能通过 Telegram 与 Bot 聊天，并由模型自主查询网页，但当前模型没有本机文件工具。交流中产生有趣的 idea 或结论时，用户希望直接说“将上述结论保存到本地”，让 Agent 自行完成文件操作，留下可以后续使用的内容。

用户希望增加的是模型可自由组合使用的基础工具能力。文件内容、命名、组织方式及具体工具调用由模型决定，不需要为保存、查找或续聊设计专门的产品流程。

## Solution

在现有 pi 会话中开放原生 `read`、`write`、`edit`、`ls`、`find`、`grep` 六个文件工具，保留已有网页工具。通过可编辑的 System prompt 约定默认笔记目录为 `D:\Course\Study\nailong notes`，由模型结合用户消息决定具体文件操作。

用户仍通过普通 Telegram 文字对话使用 Agent。Markdown 是本次讨论中的典型产物形式，内容结构、文件名和组织方式由模型自行决定，不建立固定笔记模板或格式校验。

## User Stories

1. 作为使用者，我想继续用普通 Telegram 文字与 Agent 交流，以便无需切换入口就能要求它处理文件。
2. 作为使用者，我想说“将上述结论保存到本地”，以便把交流中形成的内容留给后续使用。
3. 作为使用者，我想让模型自行决定如何组织保存的内容，以便不必每次指定笔记模板。
4. 作为使用者，我想让模型自行决定文件名，以便不必为每份产物手动命名。
5. 作为使用者，我想让模型自行决定文件组织方式，以便内容可以按实际需要安排。
6. 作为使用者，我想通过 System prompt 约定默认笔记目录，以便一般请求无需重复交代位置。
7. 作为使用者，我想在消息中指定其他本机路径，以便处理默认目录以外的文件。
8. 作为使用者，我想自行编辑 System prompt 中的目录约定，以便调整常用位置。
9. 作为使用者，我想让模型能够读取文件，以便它能依据已有内容回应我的请求。
10. 作为使用者，我想让模型能够写入文件，以便交流产物实际保存在本机。
11. 作为使用者，我想让模型能够编辑已有文件，以便内容能按对话需要更新。
12. 作为使用者，我想让模型能够列出目录内容，以便它能了解可用文件。
13. 作为使用者，我想让模型能够查找文件，以便它能定位请求涉及的内容。
14. 作为使用者，我想让模型能够搜索文件内容，以便它能按实际需要寻找相关信息。
15. 作为使用者，我想让模型自行选择和组合工具，以便应用无需为每一种文件请求编写固定流程。
16. 作为使用者，我想在网页服务不可用时仍能使用本机文件工具，以便文件能力不依赖网页服务。
17. 作为使用者，我想继续使用现有普通聊天与网页查询能力，以便增加文件工具后仍能进行原有交流。
18. 作为使用者，我想让 Agent 依据工具实际返回的结果描述操作情况，以便知道文件操作是否成功。

## Implementation Decisions

- 修改现有 pi Agent 创建逻辑，在会话的工具名称列表中启用原生 `read`、`write`、`edit`、`ls`、`find`、`grep`。当前安装版本的会话接口接受工具名称列表，并按会话工作目录创建内置工具。沿用 pi 的参数定义、执行行为和工具调用循环，不另建文件操作抽象或专用保存工具。
- 保留现有 TinyFish 网页工具；本机文件工具始终可用，不依赖 TinyFish 配置或连接成功。
- 显式选择六个文件工具，不启用 `bash`，也不使用会隐式包含命令执行工具的默认工具组合。
- 文件工具的相对路径解析沿用现有 pi 会话工作目录。默认笔记位置作为 System prompt 中的绝对目录约定，不通过修改会话工作目录或持久化目录实现。
- 更新可编辑的 System prompt，说明文件工具可用并加入已确认的默认笔记目录，替换当前禁止本机操作的过时描述。保留关于尚未支持的提醒和主动消息的事实约束。
- 默认目录仅由 System prompt 约定。按用户决定，不加入目录白名单、路径沙箱、文件审批流程或固定保存触发规则。工具实际访问范围由 Bot 进程的操作系统权限决定。
- 文件内容、文件名、格式和组织方式交给模型结合用户请求决定；不增加固定笔记模板、自动分类、索引文件或专门的笔记工作流。
- 不把“保存结论、查找旧笔记、读取后继续讨论”拆成独立功能模块或必经流程；这些场景只用于解释基础工具能力的用途。
- 延续现有消息顺序处理、本人私聊校验、文字聊天记录、重启续聊与会话重置行为。文件工具结果在当前 pi 工具调用循环中供模型使用，不为本次增量新增工具轨迹持久化或自动记忆。
- 更新使用说明，使其与工具范围、System prompt 的默认目录约定和实际文件访问方式一致。

## Testing Decisions

- 沿用现有 Telegram 消息入口的集成测试边界：从应用接收本人私聊文字开始，使用真实 pi SDK、真实文件工具、可控模型 HTTP 服务和测试临时目录，观察文件内容、工具结果参与的回复以及对外可用工具。用户已通过引用本规格调用 implement 授权按此方案实施。
- 现有集成测试已通过同一入口验证模型选择 TinyFish 工具、查询结果参与回复、重启续聊和会话重置，可直接作为此次测试的先例；现有应用测试继续覆盖身份限制和消息记录行为。
- 模拟模型服务只负责确定性地产生工具调用与回答；不替换 pi 文件工具或文件系统操作。不以此测试声称真实 DeepSeek 已能稳定理解任意文件请求。
- 验证六个文件工具向模型可用且 `bash` 未开放；在临时目录验证写入、修改、读取，以及列出目录、查找文件和搜索内容的可观察结果。不重复测试 pi 内部解析、私有状态或算法。
- 覆盖没有 TinyFish 时仍可操作文件；配置网页工具时，它们与文件工具同时可用。普通聊天无需强制调用文件工具。
- 自动测试使用临时目录和测试凭据，不写入用户的真实笔记目录，不调用真实模型或外部额度。
- 配置真实服务后人工验收一次普通对话中的保存请求，确认模型实际调用文件工具并留下可读文件。验收不要求固定标题、文件名、笔记结构或工具调用顺序。
- 验证项目既有类型检查、测试和构建门禁；不新增测试框架或额外测试接口。

## Out of Scope

- `bash`、通用命令执行和 computer use。
- 任务卡、后台任务、跨重启任务恢复、调度、主动消息和多 Agent 执行。
- 自动记忆、偏好提炼、语义检索和独立笔记索引系统。
- 目录权限隔离、审批交互及专门的保存、查找或续聊流程。
- 固定 Markdown 模板、命名规则和内容组织规则。
- Telegram 文件上传下载或新命令入口。
- pi 会话生命周期重构和工具调用轨迹持久化。

## Further Notes

- 已确认默认笔记目录：`D:\Course\Study\nailong notes`。
- 用户最终收敛的要求是“给 Agent 提供好工具，让它自己决定”。早期提出的独立场景要求和目录权限方案不作为实现要求。
- System prompt 的目录约定是模型行为指令，不是文件系统权限边界；这一点已在讨论中说明。
- 本规格是现有首版规格的后续增量，新增文件工具的决定取代首版对本机文件操作的排除，其余现有能力继续沿用。
- 用户已引用本规格调用 implement，按现有入口集成测试边界实施。
