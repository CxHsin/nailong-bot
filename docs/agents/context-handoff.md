# 检索与交接

## 按问题检索

1. 先明确本次要回答的问题，例如 Issue 是否关闭、某项保证对应哪个验收用例、某次检查为何失败。
2. 用 `rg --files` 定位候选文件，用 `rg -n` 找章节、用例名或关键字，再读取包含相关约束的完整章节。Issue 查询遵循 [issue-tracker.md](issue-tracker.md)。
3. 输出被截断时，将完整结果保存到仓库外的临时文件，按章节或行段继续读取，直到本次所需内容完整可见。截断的输出不能算作已读完。
4. 回答附上来源位置。若局部结果不足以确定含义，扩大读取范围，涵盖相关定义、例外和后续决策。

完整文档、用例账本和原始日志保留为证据；摘要用于导航。接手任务仍须读取适用的规范和决策。

## 交接模板

交接当前状态，详细过程用链接或绝对文件路径引用。按任务填写以下字段；不适用的字段可省略：

- **目标与范围**：要完成什么，权威规格或 Issue 链接，已确认的限制。
- **代码状态**：分支、基准与当前提交、相关未提交改动。
- **文件与依赖**：负责的文件、共享文件负责人、依赖工作的状态。共享 checkout 时注明写入是否已停止及停止范围。
- **验证**：实际运行的命令、结果、测试条数，以及对应提交和未提交状态；剩余失败附证据位置。
- **下一步**：具体动作或阻塞条件，需要用户决定的事项。
- **证据**：相关章节、用例、日志或 Issue 评论的指针；本地临时证据注明路径及接收方是否能访问。

接收方能定位需求与证据、识别当前代码状态并确定下一步，交接才完成。新变更发生后，更新摘要和验证状态。

## 共享工作区的验证边界

多人或多个代理共用 checkout 时，综合验证的负责人先收齐每个写入者的停写确认，注明文件范围、依赖交接及尚未完成的修改。全部相关写入停止后，再记录受检提交和工作区差异，运行综合检查；确认停写不等于获准启动新的代理。

检查期间保持相关源码、夹具、配置和生成输入稳定。若这些文件发生变化，旧结果只适用于原来的状态：记录变化，针对受影响的保证重新验证，再更新交接。提交负责人核对受检内容与实际暂存差异一致后才能提交。仅靠检查结束时比较文件摘要不能证明期间没有并发修改，停写确认仍然必要。
