# Runtime progress and migration

Production Telegram and CLI use ordinary Markdown assistant output. A normally completed model step with tools settles an independent progress unit; a step without tools settles the final answer. The final answer is complete on its own. JSON status/result/final remains only in the retained legacy application and explicitly selected compatibility tests.

Progress streams through temporary drafts and becomes a fixed, independent Telegram message when settled. Final answers are delivered separately. Telegram progress uses an expandable quotation and visible title; an API that rejects the expandable attribute falls back to a normal quotation. Long bodies use the existing structural HTML pagination. The default draft cadence is 250ms, within the 500ms scheduling target when no request is in flight or rate-limited; network and client latency are outside that target.

The auxiliary model produces only read-only Run Summaries from task text, earlier explanations and committed tool facts. Defaults are 15 seconds of silence, at least 60 seconds between calls, and five attempts per Run. It has no tools. No new fact means no new call. It does not replace a live primary-model draft; primary text, newer tool facts, cancellation or Run termination invalidate late results. `PROGRESS_MODEL` selects its model and `PROGRESS_SUMMARY_OPTIONS` controls `silenceMs`, `intervalMs`, and `maxCalls`. Usage is recorded under the progress purpose.

Settled progress and valid summaries enter model replay with provenance, independently of delivery. Drafts, activity wording and Delivery Facts do not. Akasha still indexes only user/assistant answer content whose delivery is confirmed, including historical stage results; process explanations and Run Summaries are excluded. Tool results remain execution facts, not memory content.

Each formal content unit has an immutable page plan and per-page attempt/outcome records. Known rejection is retried at most three times respecting retry_after; unknown outcomes and attempts without a committed outcome cannot be resent automatically. A failed progress delivery does not stop final delivery. API success followed by log-commit failure remains an unknown attempt. Startup records active Runs as interrupted and sends nothing; it never resumes models, tools or notifications automatically.

## Event-store handover

Stop the old writer before opening production with this version. The new store is `runtime-v2.sqlite`. The migration reads the unique existing `events.sqlite` or `runtime.sqlite` as a read-only snapshot, or `events.jsonl` when there is no SQLite source. It copies all source events in order and keeps their IDs, association fields, text, learning/exclusion facts, archive references and delivery records. It preserves source files and verifies the destination before committing the migration marker. JSONL identities use the previous event-identity algorithm. Existing settled status/progress gains replay eligibility; invalid or discarded content does not gain eligibility through migration.

The destination records a source digest, count and association report, readable through `migrationReport()`. It checks Run ownership, model/content association, tool pairing, page/attempt/outcome association, archive source IDs and Unicode memory source ranges. Contradictory recorded associations stop handover. Missing historical facts remain missing and are listed as exceptions; `referencesVerified` is false in that case, without inventing delivery or execution outcomes. `referencesPreserved` means association fields were copied unchanged, not that every old reference resolved.

Reopening verifies that the retained source has not changed; it rejects mixed old/new writers, malformed input, duplicate identity, multiple old stores, archive verification failure and an unverified nonempty destination. A failed conversion rolls back destination events and does not select an empty history. Re-running a completed migration does not duplicate old content or emit deliveries. Existing checkpoint and memory indexes are derived caches and are revalidated/rebuilt from the new prefix; original learning and exclusion facts remain intact. Writer shutdown is an operational prerequisite, not a process lock: do not run two entry points concurrently against the same data directory.

Rollback requires stopping the new writer and deliberately selecting the retained old source with the old application. Any new v2 events written after handover must be preserved separately and reconciled before a later handover; rollback is not an automatic merge of two writers.

## Acceptance

The automated boundary is production Pi/Host/Channel behavior with an external Provider fixture and a real temporary store. Migration is checked through old-store and new-store public readers, not raw row assertions. Real-model cases cover multi-step lookup, long tools, changed direction and quick answers. Real Telegram acceptance must name an authorized test chat and check native draft lifecycle, per-segment formal messages, folded and fallback rendering, long content, and independent final answers. Fake-transport success alone does not establish live client quality.
