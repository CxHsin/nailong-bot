# Runtime progress and migration

Production Telegram and CLI use ordinary Markdown assistant output. Responses public message signatures retain `phase: commentary` or `final_answer` and a separate text-unit identity. A completed commentary item settles an independent progress unit, even when there is no tool call; a commentary-only response continues the execution instead of ending the Run. For Providers without a public phase, text alongside tools is progress and a normally completed step without tools is the final answer. The final answer is complete on its own. Historical JSON status/result/final encoding and data readers remain for old records; the legacy application and live JSON parser/writer were retired in #149.

Both Provider routes normalize through one public-text phase adapter. Host text events and `text_finalized` facts carry `phase` and `phaseSource`: native fields produce `native`; ordinary tool-step text produces `commentary / tool-boundary`; normal tool-free completion produces `final_answer / terminal-boundary`. While an ordinary delta is arriving its phase is `unresolved / pending`, so it can stream immediately without claiming the Run is complete. A step dispatching tools remains progress even if its native final tag conflicts with the call. Provider names never determine this mapping, and reasoning blocks never enter it. Ordinary Providers keep their natural tool/stop control behavior; no extra progress tool or text framing is added.

Production Telegram uses one native Rich draft ID for the entire Run. Preparation states, tool activity and public model findings accumulate in one progress journal, preserving each original text-unit identity and Markdown. States are encoded as literal text. A completed finding stays in the journal instead of being sent separately. Ordinary unresolved text can stream in the journal; when classified as final it moves outside the details region. The final answer streams outside the journal on the same draft. Snapshots coalesce at roughly 250 ms and unchanged drafts refresh before their 30-second expiry.

Live journal snapshots specify `<details open>` on every update. At the terminal, settled commentary and real states are saved once with `<details>` (collapsed by default), then the final answer is delivered separately. Failed/cancelled Runs save settled commentary and states only; discarded and unfinalized text is excluded. Aggregation belongs to the Channel and does not merge or rewrite model facts, phase metadata or replay. Journals paginate only beyond Rich's 32768-character message capacity; each page retains a complete details container. Final-answer pages retain the conservative 3500-source-character limit. Markdown pagination reopens code fences, nested list/quote containers and inline emphasis. Oversized drafts show the latest bounded journal page with final preview when it fits, otherwise the final preview alone; saved content retains every settled page. Live updates specify a default rather than remembering a client toggle: manually collapsing a draft is reset to open on its next update. Saved journal messages no longer refresh.

Drafts and formal sends use only `sendRichMessageDraft` and `sendRichMessage` with the `markdown` field; the production Channel does not render HTML or fall back to ordinary messages. A rejected partial Markdown snapshot leaves the previous valid native preview visible; later snapshots retry Rich after backoff. Journal planning errors (such as an oversized table row) are recorded and skip that journal snapshot/save without stopping the Run or its final answer; a later valid journal can recover. Transient draft failures respect retry_after or back off without preventing separate final delivery. An unavailable Rich endpoint is a delivery failure, never a switch to another format.

Journal delivery has a three-second deadline. Failure or an unknown outcome disables further progress sends, with no automatic retry; already issued network requests can still resolve afterward, but cannot initiate later page requests. Final delivery proceeds after the bounded wait. Progress receipt events contain journal segment IDs, message IDs and delivery state, carry `contextPolicy: exclude`, and are not model or Akasha content. Startup does not resend retained progress. Slash commands return directly without a progress journal. Only visible commentary is collected; Provider thinking is never collected.

Production Pi no longer starts auxiliary Run Summary calls. Progress comes from the executing model's public commentary, using phase fields when present. It reports grounded new findings and the next step, not hidden reasoning or a tool-name list. The current Host still accepts an injected `summarizeProgress` worker, exercised by `test/runtime-progress.test.ts`; production Pi provides no such worker. Old settled Run Summaries remain replayable with their recorded provenance; `PROGRESS_MODEL` and `PROGRESS_SUMMARY_OPTIONS` do not select a production progress model.

Reference: Codex [Responses SSE mapping](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/sse/responses.rs) distinguishes output-text deltas and public message phases. Telegram [sendRichMessageDraft](https://core.telegram.org/bots/api#sendrichmessagedraft) requires a formal send to persist a completed draft; completion preserves content and layout. Runtime status uses the native [Rich Markdown details extension](https://core.telegram.org/bots/api#rich-markdown-style) in both drafts and formal messages; it does not require an HTML renderer or a change to the `markdown` API field.

Settled progress and valid summaries enter model replay with provenance, independently of delivery. Drafts, activity wording and Delivery Facts do not. Akasha still indexes only user/assistant answer content whose delivery is confirmed, including historical stage results; process explanations and Run Summaries are excluded. Tool results remain execution facts, not memory content.

Each formal content unit has an immutable page plan and per-page attempt/outcome records. Known rejection is retried at most three times respecting retry_after; unknown outcomes and attempts without a committed outcome cannot be resent automatically. A failed progress delivery does not stop final delivery. API success followed by log-commit failure remains an unknown attempt. Startup records active Runs as interrupted and sends nothing; it never resumes models, tools or notifications automatically.

## Event-store handover

Stop the old writer before opening production with this version. Run `npm run migrate` for an explicit offline handover: it validates sources/archives, backs up the complete data directory under `data/backups/` (respecting `AGENT_DATA_DIR`), records file hashes, migrates and saves a report. SQLite backups include committed WAL content. It never calls a model or sends a message. Then start the Bot normally.

The new store is `runtime-v2.sqlite`. The migration reads retained `events.sqlite`, `runtime.sqlite` and `events.jsonl` as read-only snapshots. Empty SQLite placeholders do not count as competing histories. Identical SQLite copies or complete identity-and-content prefixes share a verified source; the longest history is selected. A retained JSONL must match the SQLite payload prefix in full; its distinct import identities are not used to deduplicate unrelated SQLite writers. Divergent histories and a JSONL-only tail stop handover instead of silently discarding events. Source selection and every retained representation's digest are saved and checked on reopening.

It copies all selected source events in order and keeps their IDs, association fields, text, learning/exclusion facts, archive references and delivery records. It preserves source files and verifies the destination before committing the migration marker. JSONL-only identities use the previous event-identity algorithm. Existing settled status/progress gains replay eligibility; invalid or discarded content does not gain eligibility through migration.

The destination records a source digest, count and association report, readable through `migrationReport()`. It checks Run ownership, model/content association, tool pairing, page/attempt/outcome association, archive source IDs and Unicode memory source ranges. Contradictory recorded associations stop handover. Missing historical facts remain missing and are listed as exceptions; `referencesVerified` is false in that case, without inventing delivery or execution outcomes. `referencesPreserved` means association fields were copied unchanged, not that every old reference resolved.

Reopening verifies that the retained source has not changed; it rejects mixed old/new writers, malformed input, duplicate identity, divergent histories, archive verification failure and an unverified nonempty destination. A failed conversion rolls back destination events and does not select an empty history. Re-running a completed migration does not duplicate old content or emit deliveries. Existing checkpoint and memory indexes are derived caches and are revalidated/rebuilt from the new prefix; original learning and exclusion facts remain intact. Writer shutdown is an operational prerequisite, not a process lock: do not run two entry points concurrently against the same data directory.

Rollback requires stopping the new writer and deliberately selecting the retained old source with a historical version of the old application; that executor is no longer present in the current version. Any new v2 events written after handover must be preserved separately and reconciled before a later handover; rollback is not an automatic merge of two writers.

## Acceptance

The automated boundary is production Pi/Host/Channel behavior with an external Provider fixture and a real temporary store. Migration is checked through old-store and new-store public readers, not raw row assertions. Real-model cases cover multi-step lookup, long tools, changed direction and quick answers. Real Telegram acceptance must name an authorized test chat and check native draft lifecycle, per-segment formal messages, identical Rich Markdown formatting, long content, rejected partial snapshots and independent final answers. Fake-transport success alone does not establish live client quality.
