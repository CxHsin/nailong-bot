# 规格：上下文输入意图路由与自然语言工作控制

Based on #214

正式规格：[Issue #215](https://github.com/CxHsin/nailong-bot/issues/215)，已标记 `ready-for-agent`。以下正文为发布内容的本地归档。

本规格依据 2026-10-16 已确认的设计结论形成。主要测试边界已由用户确认：从 Assistant Service 接收原始输入，经过真实持久队列及 Durable 执行，观察模型请求、工具效果、输出与重启恢复；外部模型和 herdr 使用受控响应，另做少量真实链路验收。规格与实现验收分别记录，不表示功能已实现。

## Problem Statement

当前 Personal Agent 把普通消息按 FIFO 排队，只允许用户通过显式 `/steer` 补充当前工作。这使“报表改成 CSV”“刚才那个先别做”等自然表达无法及时影响对应工作；用户必须理解执行器的控制命令。已有后台 helper 虽然释放了主 Bot，但它的补充仍依赖主 Bot 当前轮次处理，无法保证越过无关工作及时送达。

仅对最新文字分类也不足以解决问题：消息可能引用近期对话、尚未开始的请求或已有后台委派；一个 Processing Turn 或 Input Batch 又可能包含多个独立目标，不能把批次身份误作取消范围。需要在保留持久接收、去重和执行恢复的基础上，理解消息与实际工作的关系。

## Solution

用户正常发消息即可交办、补充、修改或取消工作，移除用户输入入口 `/steer`。独立快速模型读取当前消息、回复关系、有限近期对话和实际工作列表，返回动作及目标；程序据此执行确定的调度规则，主 Bot 负责详细理解、实际工作与必要澄清。

无关新请求仍按 FIFO；当前工作的补充在可接收输入边界生效；排队工作的修改保留原位置；明确取消尽快发起中断。耗时工作由 herdr helper 在后台执行，明确给 helper 的补充及时转交，不等待主 Bot 完成无关工作。

分类不可用或需要看图才能理解时，保留原始用户输入及附件，通过普通队列交给同一个主 Bot，并单独附带未判定原因。原消息不改写为系统生成的用户要求，不因分类失败自动执行取消，也不丢失。

## User Stories

1. 作为用户，我希望自然语言补充当前工作，以便不必输入 `/steer`。
2. 作为用户，我希望“刚才那个”能结合近期对话理解，以便正常使用指代和追问。
3. 作为用户，我希望回复某条 Telegram 消息时保留回复关系，以便准确指向对应工作。
4. 作为用户，我希望新问题与旧工作的补充能分开，以便无关消息不会擅自改变当前目标。
5. 作为用户，我希望无关的新请求继续按 FIFO，以便处理顺序可预期。
6. 作为用户，我希望当前工作的补充在下一个输入边界生效，以便无需等整项工作结束才修改要求。
7. 作为用户，我希望运行中的工具不会仅因普通补充被终止，以便保留正在产生的结果。
8. 作为用户，我希望多条补充保留各自顺序和身份，以便后一条明确纠正可以覆盖前一条要求。
9. 作为用户，我希望排队工作的修改保留原位置，以便不会因为改了格式而重新排到队尾。
10. 作为用户，我希望跨过无关消息补充先前请求，以便不会先执行旧要求再返工。
11. 作为用户，我希望直接取消尚未开始的工作，以便不浪费执行资源。
12. 作为用户，我希望明确取消正在执行的工作时尽快发起中断，以便不必等待当前轮次完成。
13. 作为用户，我希望取消只影响指定目标，以便同批其他工作继续保留。
14. 作为用户，我希望取消保留已有成果，以便之后可以查看或重新利用。
15. 作为用户，我希望“已停止”有真实执行证据，以便不会把发出中断误认为工作已经停止。
16. 作为用户，我希望唯一可指代工作能被直接定位，以便简单的“那个别做了”无需重复解释。
17. 作为用户，我希望有多个合理对象时被问清楚，以便不会取消错误工作。
18. 作为用户，我希望明确说出对象时采用指定对象，以便不被最近一次活动错误覆盖。
19. 作为用户，我希望一句话可以包含取消与新请求，以便不用拆成多条消息。
20. 作为用户，我希望新请求不必等取消完全确认才被接收，以便两件事分别推进。
21. 作为用户，我希望耗时工作在 helper 后台运行，以便继续和主 Bot 交流。
22. 作为用户，我希望给后台 helper 的明确补充及时送达，以便不被主 Bot 的无关工作挡住。
23. 作为用户，我希望 helper 转交区分已发送和已采纳，以便知道补充是否真正生效。
24. 作为用户，我希望停止 helper 时检查它启动的实际进程，以便 Escape 后仍运行的任务不会被遗漏。
25. 作为用户，我希望空闲时立即处理已有输入，以便不为合批等待固定时间窗。
26. 作为用户，我希望同批消息保留各自目标和边界，以便不同事项不会被当成同一目标。
27. 作为用户，我希望判断失败后原话继续进入主 Bot，以便不会丢失交办或被改写意思。
28. 作为用户，我希望图片原样交给支持视觉的主 Bot，以便无需把图片内容重新打字。
29. 作为用户，我希望尚未执行的补充或取消不会被报告为成功，以便理解真实进度。
30. 作为用户，我希望重复投递同一条消息不会重复修改或发送，以便通道重试没有重复效果。
31. 作为用户，我希望服务重启后继续原输入的投递与执行，以便不必重新交办。
32. 作为用户，我希望未知投递结果先核实，以便不把同一补充再次发给 helper。
33. 作为用户，我希望工作在判断期间完成后仍能正确处理新要求，以便补充转为基于成果的后续修改。
34. 作为用户，我希望 `/reset` 保留已有工作及原输入，以便重置上下文不等于取消。
35. 作为用户，我希望已取消的工作不会因重启或普通恢复而自动继续，以便取消具有持续效果。
36. 作为用户，我希望分类器不使用已遗忘的对话材料，以便既有遗忘规则继续有效。
37. 作为用户，我希望不同 Conversation 的输入和工作互不串用，以便目标始终归属正确。
38. 作为维护者，我希望分类模型独立配置且调用有界，以便控制延迟、费用和故障影响。
39. 作为维护者，我希望已有队列和执行记录继续可恢复，以便升级不丢弃排队消息或已接收补充。
40. 作为维护者，我希望测试验证实际输入、效果和恢复，以便分类结果正确不能掩盖投递错误。

## Implementation Decisions

### 1. 职责及模块边界

- Channel 继续负责鉴权、接收和交付；Assistant Service 负责持久接收、意图路由、队列调度及控制；Pi Durable 保存主模型与工具执行进度；herdr 继续执行已委派工作。
- 在 Assistant Service 内增加有限的意图判断和动作分发能力。分类模型不获得执行工具，不能输出任意 Shell 命令或临时 helper 身份供程序执行。
- 引用已有 Input Event、Processing Turn、Input Batch 和 Helper Observation 的持久身份，增加必要的目标关联，不另建通用 Task 平台、审批引擎或替代执行日志。
- Telegram 和 CLI 的普通直接输入走同一应用级路由；herdr 返回继续作为内部执行材料，不伪装成用户消息、不重新分类为用户命令。既有来源优先级和直接输入高于后台结果的规则保留。

### 2. 持久接收与输入契约

- 先持久接收原始输入、来源去重键与到达序号，再开始分类或确认接收。分类模型的耗时不能阻止接收后续消息，也不能占用主 Bot 的长轮次锁。
- 保留用户原文、图片、Conversation、来源、输入身份及回复信息。Telegram 必须把已获取的回复消息身份传到 Assistant Service；能由已有原输入或发送回执关联目标时提供该关联，不能猜造不存在的回复对象。
- 将用户实际文字与通道为无文字图片生成的提示分开记录；“请分析这张图片”等默认说明不能冒充用户明确的路由意图。
- 发送回执或回复所指的输出包含多个目标时，保留多个关联供判断，不能因它们共用一条 Telegram 回复就强行定位其中一项。
- 同一来源身份的重复消息返回原接收与路由进度，不生成第二套动作；相同正文但不同原消息身份仍是不同输入。
- 路由未完成前的输入不能被普通领取路径抢先当成已分类的新目标执行。分类决定和动作领取须使用可恢复的持久交接，接收身份跨普通、补充和控制路径统一去重。

### 3. 独立模型配置与有界调用

- 分类器独立引用现有模型目录中的一个别名，复用既有 provider、凭据和协议配置；不固定供应商或具体型号。主 Bot 的模型切换不改变分类器选择，也不继承主轮次的重试预算。
- 未设置分类模型时明确记录未配置并使用原输入兜底；设置了不存在或不可用的别名时启动配置校验报错，不悄悄改用主模型。已合法配置的模型发生运行故障时，按单条输入降级。
- 本规格采用以下默认值：每次判断总超时 8 秒，最多 8,192 个估算输入 token，最多 1,024 个输出 token，近期对话最多 6 个用户轮次及其已确认助手文字。输入、输出总预算还须受分类模型实际上下文窗口限制。
- 模型别名、超时及上下文预算可通过应用配置覆盖，并有正数及模型窗口校验。使用现有 token 估算方法；同一受检状态下预算策略必须可重复。
- 每条输入正常只做一次非流式、无工具的判断；使用模型支持的低推理配置，不增加同步重试、向量检索、训练流程、跨消息缓存或冷却框架。超时后到达的结果不得继续分发动作。
- 普通命令入口继续按已支持的命令规则执行，不让分类器重新解释 `/reset`、`/resume`、`/model` 等确定命令；被删除的 `/steer` 不保留别名式快捷行为。

### 4. 判断上下文

- 当前用户文字优先且保持完整；如果它本身无法放入预算，直接降级，不能截掉限定对象或否定词后执行补充、取消。
- 近期材料只包含当前 Conversation、当前可见上下文范围内的用户原话和已确认助手文字，保留角色、原输入身份和时间；排除草稿、完整工具输出、其他会话及已失效的遗忘来源。`/reset` 前的普通聊天不重新混入近期对话。
- 工作列表来自实际队列、当前执行及已登记 helper，包含稳定目标引用、简短目标、状态、关联原输入和执行或 helper 身份。同批不同目标分别表达；helper 的完成标记和已回传结果不直接等同于整个目标完成。
- 新登记的 Helper Observation 同时保存对应的原始输入目标引用和简短交办摘要；可从当前明确的目标关联自动取得，但一轮有多个目标时必须显式区分，不能默认绑定整批。历史记录缺少关联时保留待核查状态。
- 工作摘要优先依据实际交办及已有可追溯资料生成，单项默认不超过 512 个 Unicode 字符；分类不额外调用模型生成摘要，也不默认读全部 prompt 文件或工具档案。升级后的历史 helper 缺少可用摘要时可有限读取原 prompt，读取失败则标记信息不足。
- 预算优先保留当前输入、明确回复对象和工作身份，再加入最近对话及其他摘要。省略工作候选时显式注明列表不完整；模型和程序均不得把截断后的一个候选当作全局唯一工作。上下文不足以唯一定位则澄清或降级。
- 历史对话、helper 摘要和附件内容保持资料身份；它们不能自行授权对另一个工作执行取消。当前真实用户输入决定动作意图，运行时已知身份限制目标范围。
- 复用现有遗忘与可见性过滤，不增加长期记忆召回、写入或新的全量会话投影。工作状态仍来自执行事实。

### 5. 动作与目标契约

- 判断结果表达一个原输入对应的有序动作列表。每项包含动作种类、原文对应片段、目标引用或澄清候选；动作种类限定为独立请求、补充、取消和需要澄清。路由器另外记录不可判定及降级原因。
- 目标只能引用本 Conversation 中已提供、可复核的工作身份。JSON 解析失败、未知动作、缺失必要字段或不存在的目标不能被当作有效控制结果；在分发任何动作前完成整个结果的结构与身份校验。
- 仅有一项可指代工作且上下文足够时可直接定位；用户明确指定时采用指定对象；存在多个合理对象时交主 Bot 提问，提问前不试探性修改或取消候选对象。
- 一条消息中的多个独立要求分别保留动作身份，但仍关联同一原始 Input Event，原文不按拼接后的模型摘要覆盖。已知目标的控制动作不因同条消息包含新请求而失效。
- 同一目标的补充和取消按原接收序及原文次序实施，防止分类响应乱序使旧要求覆盖新要求。对独立目标保留原 FIFO 锚点；不因控制动作被及时处理而把其他独立新请求提到队首。
- 取消之后的补充不能自动复活已取消工作；只有当前用户明确要求恢复或重新交办时才作为新请求处理。`/resume` 仅保留原有暂停恢复范围，不复活取消项。

### 6. FIFO、合批与排队修改

- 独立新请求不打断同级正在处理的直接输入；主 Bot 空闲或结束当前短轮次后，读取当时已接收的有限输入快照。可以一轮处理多项目标，不等待未来消息或固定时间窗。
- 确认新批次内容前，完成快照范围内输入的关系处理或有界降级；不能在已经接收的修改尚待分类时先领取同一快照中的旧版要求。快照外后来输入按对应目标的最新状态接入。
- 补充关联到原目标，保留原目标 FIFO 位置及补充的独立身份。夹在原请求和补充之间的无关输入保持自身位置。命令、来源或优先级的既有批次边界保留，目标关联不依赖消息在批次内相邻。
- 排队请求的取消持久撤销该目标及其不再需要的待执行动作，保留接收和取消记录，不实际启动旧要求。
- Input Batch 是执行与交付容器，不是用户目标。取消同批一项不能把其他项标为取消或完成；其他项保留原顺序、身份、成果和继续责任。

### 7. 主 Bot 当前工作的补充与取消

- 复用 Durable 已有的输入边界和补充消费机制。目标明确的自然语言补充加入当前工作，在下一个支持的边界按序读取，不仅因为补充就终止正在运行的工具。
- 每条补充关联具体目标、原输入和执行提交，区分待投递、已提交和已消费。当前执行已结束或提交确认未消费时，转为基于现有成果的后续处理，不同时进入当前与后续执行。
- 明确取消尽快发起对应中断，停止安排该目标的新步骤。中断请求、执行退出与外部进程真正停止分别核实；退出或 abort 本身不证明外部副作用已撤回。
- 执行器只有共享批次级中断能力时，可以中断共享 Processing Turn，但只将指定目标置为取消。其他目标保留 Durable 已确认结果并重新调度续接，不能被整批丢弃或从头重复效果。
- 对无法确认的外部效果沿用既有对账与暂停规则；无法确认已停止时诚实报告未知。取消不删除既有文件、成果或原始记录。

### 8. helper 的及时控制路径

- 在 Assistant Service 增加面向已登记 helper 的有限控制分发，与主 Bot 普通执行队列分开。它只转交已识别的用户补充或发起对应取消，不运行另一套自由工具循环，也不重派 helper。
- 执行前核对保存的 session、agent、pane、workspace、工作目录与实际状态；身份不匹配、对象不存在或状态未知时保留原消息及现场，交主 Bot 核查，不改投另一个 helper。
- 使用当前安装 herdr 支持的输入接口传递原要求和稳定补充身份，命令参数通过结构化参数传递。模型只选目标和原文内容，不能控制程序参数模板之外的执行行为。
- 补充按目标顺序串行转交，目标不同不共享一个等待整项工作完成的锁。CLI 返回、prompt 回显或旧的 working 状态只能证明有限提交事实；单独记录发送已确认、采纳已确认或待核实，并保留各自证据。
- 不把观察到原轮次结束当作新补充被采纳。通过补充身份对应的真实输出或可核实执行证据确认采纳；无法确认时只报告已转交或待核实，不虚构已生效，也不为确认而重复发送。
- 已明确拒绝且没有发送的请求可以保留待处理；可能已发送但结果未知时先对账，不套用模型请求重试。helper blocked 时不假定提交成功。
- 取消沿用真实 helper 身份中断和所属进程核验：Escape 之后检查任务启动的进程是否仍在运行，只停止确认属于该工作的进程，保留共享服务和其他任务。未知归属时不执行宽泛终止。
- 快速控制结果作为内部执行材料返回主 Bot；状态更新可以及时通知用户，但不能另造用户消息或直接写入长期记忆。后续 helper 回报仍经成果验收，不能自动续跑已取消目标。

### 9. 状态复核、兜底与用户说明

- 动作执行前重新核对目标身份与实际状态。工作在分类期间完成时，补充成为基于成果的后续修改；已结束工作的取消报告真实状态，不向原执行重复发送停止。
- 原消息因超时、provider 错误、未配置模型、预算不足、结果无效或需要视觉理解而兜底时，保留原位置进入普通队列。主 Bot 接收原始用户身份及内容，运行时另附未判定原因和已确认的动作进度，不把路由说明拼进用户正文。
- 完全未分发的兜底输入明确说明尚未执行补充或取消。复合输入已经部分执行时，只对未完成动作兜底，并告知已执行部分；不得使用“尚未执行任何动作”的错误说明，也不得让主 Bot 重做已确认部分。
- 有文字的图片输入可以只按文字与工作上下文判断；纯图片、文字不足以支持动作或模型要求视觉理解时，把原图交给支持视觉的主 Bot。分类器不下载新附件或自行调用 OCR。原有媒体接收能力范围不扩大。
- 主 Bot 空闲时开始兜底轮次，忙碌时等待当前短轮次。对无法即时处理的补充或取消给出一次简短、真实的状态说明，明确工作尚未因该消息停止；内部错误细节保留给诊断，不要求用户了解路由实现。

### 10. 持久化与恢复

- 原输入、快照来源、模型别名与预算、判断结果、动作身份、目标关联、执行或 helper 提交身份、已确认投递及消费进度需可持久对账。目标关联必须能表达一批多目标及一输入多动作，不依赖数据库表名作为外部契约。
- 接收、路由决定落盘、领取和外部发送之间均建立可恢复的交接。模型判断尚未提交且未发生动作时可恢复判断；决定已落盘时复用决定并复核目标状态；已确认效果复用，未知外部发送先核实，不盲目再次提交。
- 取消是持续状态，不作为临时抢占自动恢复。关闭服务、重启、`/reset` 和普通 `/resume` 不能取消取消标记；新的明确用户交办通过新输入身份表达。
- 原输入去重、动作去重和消费记录跨应用队列、Durable 和 helper 通道关联。已消费的补充不能在普通队列再次执行；已经部分完成的复合输入只恢复剩余部分。
- 继续保留数据目录单服务所有权、后台结果低优先级、暂停工作明确恢复、发送未知结果先核实等现有保证，不宣称跨系统 exactly-once。
- 路由近期材料遵守已有遗忘、纠正和 reset 可见性规则；失效材料及其摘要不能靠路由快照重新进入模型。原始执行身份与无关工作进度保留。

### 11. 入口迁移及操作说明

- 移除 Telegram 帮助、命令分发和面向用户文档中的 `/steer` 特殊入口与用法。新收到的 `/steer` 按不支持命令处理，提示直接用自然语言交办，不剥除前缀后悄悄执行。
- 可以复用 SDK 内部 steering 能力；内部执行机制与退役的用户命令分开。更新当前说明及对应测试，旧研究和验收保留历史日期与基准，不把历史行为改写成已迁移行为。
- 对当前 Durable 数据目录做兼容升级，不清空会话、排队输入、暂停项、输出回执或已登记 helper。已有未完成显式补充按原身份和提交事实排空或迁移；发送未知先对账，不把旧补充重新当作新自然语言输入执行。
- 原有命令、CLI、Telegram 图片及成果文件发送保持可用。运维可查看所用分类模型、是否降级和动作处理状态；记录有限的原因、关联身份与证据，不输出凭据或全量工具资料。

## Testing Decisions

### 用户已确认的主要边界

以 Assistant Service 的公开输入、输出订阅、等待及同目录重开作为主要测试入口。保留真实持久队列、Durable 执行及目标关系，只替换外部模型和 herdr 响应；通过本地 HTTP 模型夹具检查真正送出的消息、工具调用、文件或进程效果和实际输出。

沿用现有普通排队、显式补充边界、helper 互动、Telegram 接入、原图传递及子进程强杀恢复测试的做法。把旧显式命令用例改为自然语言意图驱动，同时保留有价值的消费去重、执行边界和重启保证。不要以私有方法、表名、prompt 全文快照或 mock 调用次数代替行为验证。

受控分类器只用于可重复安排判断结果、超时和竞态；不能据此宣称真实模型能理解中文。真实模型验收单独记录逐项输入、分类、目标、耗时和结果，不据小样本宣称总体准确率。

### 必须覆盖的验收场景

| 场景 | 必须观察的外部行为或效果 |
| --- | --- |
| 独立输入 A 运行时收到 B、C | A 不被普通新请求中断；B、C 保持 FIFO，允许同一后续轮次分别处理 |
| 运行中的工作收到自然语言补充 | 原工具仍按边界执行，下一模型请求带补充原文和身份，普通无关输入不混入当前工作 |
| 多条补充及重复投递 | 按原顺序消费，每个来源身份只生效一次，后续纠正不会被慢返回的旧分类覆盖 |
| 排队的报表、天气、CSV 修改 | 报表首次执行即采用 CSV，天气原位置不变，各输入身份保留 |
| 取消排队目标 | 对应目标没有真实模型/工具工作效果，同批其他目标仍处理 |
| 一句话取消并新增请求 | 取消及时发起，新请求被独立接收并按 FIFO；取消未知不会丢失新请求 |
| 只取消同批中的一项 | 剩余目标保留进度继续，已确认工具效果不重复，取消项不被当作已完成 |
| 单一对象、明确指定和多对象歧义 | 前两者定位正确；歧义仅提问，不对任何候选产生停止或修改效果 |
| Telegram 回复关联 | Channel 到实际分类请求保持回复身份，已知原消息或发送回执定位正确，不伪造未知回复 |
| 分类器与主 Bot 同时工作 | 分类请求不等待主 Bot 当前模型或短工具结束；普通请求仍不越过 FIFO |
| 主 Bot 忙于无关工作时给 helper 补充 | 不释放主轮次也能观察到正确 helper 的真实提交；其他 helper 没有收到补充 |
| helper 仍在旧轮次 working | CLI 返回或旧状态完成不被记为新补充已采纳；后续真实证据才确认 |
| helper blocked、身份变化或投递未知 | 没有错误改投和盲重发；原消息保留，用户获知待核实状态 |
| helper 停止后仍有子进程 | “已停止”必须晚于相关活动停止的证据；无关进程和共享服务保留 |
| 分类期间目标完成或状态改变 | 不向过期执行注入；补充成为基于成果的后续修改，取消报告实际状态 |
| 分类超时、报错、无效结果、未配置 | 原输入经普通队列被同一主 Bot 接收，角色/原文/身份不变，内部路由说明分离，未执行控制动作 |
| 超时后分类结果迟到 | 迟到结果不取消、不补充，原输入仍只走既定兜底路径 |
| 当前文字或候选列表超预算 | 不截掉要求后误取消；省略候选不能触发“唯一对象”推断 |
| 图片只有默认提示或必须看图 | 文本分类器没有收到伪造用户意图；主 Bot 实际收到原图及未判定说明 |
| 复合输入部分动作已确认后失败 | 仅剩余动作进入恢复或主 Bot，已确认取消/发送不重复，说明准确 |
| 输入落盘后、决定落盘后及发送附近强杀 | 重开同目录仍保留原身份和进度；已确认不重复、未知先核实，不从新消息起步 |
| 取消后重启、reset 和 resume | 取消项不自动恢复，无关目标、暂停项和队列继续遵循原保证 |
| 近期材料经过 reset 或遗忘 | 实际分类请求不再含失效对话/派生摘要，无关工作身份与进度保留 |
| 两个 Conversation 及来源重复键 | 目标、近期材料、控制效果和回报不串会话，正确区分同文不同身份 |
| 升级时存在旧显式补充与已知提交 | 沿用原身份核实消费；新 `/steer` 不再有特殊效果，帮助和当前说明一致 |
| 模型配置和调用上限 | 分类使用所选独立别名和预算；主模型切换不改变它，失败无同步重试叠加 |

跨进程恢复沿用子进程在可观测边界强杀后重开同一目录的方式，以实际模型输入、投递证据、原始身份及文件/进程活动为断言，不只检查日志或完成标记。必要的低层回归只覆盖集成边界无法稳定定位的持久化保证。

### 真实链路及交付检查

- 使用实际配置的分类模型验证中文新请求、近期指代、跨无关消息补充、明确取消、多目标歧义及复合动作，逐条记录；显式取消误投、跨会话投递或未停止却报告停止均是阻断问题。
- 通过真实 Telegram 验证自然语言补充、回复定位、图片兜底和结果交付；通过真实 herdr 验证主 Bot 忙碌时的及时补充、采纳证据及真实进程停止。使用本次受控工作，保留实际身份、输入、输出及恢复证据，不触碰其他工作。
- 实施交付运行相关行为与恢复测试、全仓测试、类型检查、构建和文档链接检查，记录实际命令、测试条数、受检提交及结果。发布本规格本身不等于上述实现检查已经通过。

## Out of Scope

- 不实现按意图选择主回答模型的 Magpie 路由组，不引入嵌入、训练或多级分类器。
- 不建设通用任务平台、统一审批、跨项目编排、跨主机调度或新的后台 agent 框架。
- 不新增 cron、邮件、Slack、群聊、多用户或此前未支持的任意文件输入连接器。
- 不修改长期记忆的总体策略，不通过完整历史、工具日志或全量文件堆入分类器。
- 不保证任意工具可瞬时停止、跨系统 exactly-once 或已发生外部效果回滚；取消也不物理删除成果。
- 不迁移历史旧 Host 命名空间或清空现有 Durable 数据来规避升级；只处理本功能相关的当前输入与补充记录。
- 本次 to-spec 不实施运行代码、不创建实现任务、不推送 Git、不部署或合并。

## Further Notes

本规格基于已确认的结论 #214 和 ADR-0013。它局部替代 #201 中普通消息不能隐式补充、用户必须使用 `/steer` 的输入约束；现有持久队列、Pi Durable、herdr、媒体及上下文职责保留。

当前基线为 development 的 `479ec10`：文档设计已确认，生产仍使用旧 FIFO 与显式命令路径。规格中的配置默认值及协议细化是本次综合得到的实施约束，不回写为先前访谈已经逐项选择的参数；实现可以调整内部结构，但变更用户可见行为或这些默认值时须明确更新依据和验收。

后续实现任务另建 Issue，以本规格为 Part of 关联。结论、规格和实现验收分别记录，规格发布不关闭设计或宣称功能已上线。
