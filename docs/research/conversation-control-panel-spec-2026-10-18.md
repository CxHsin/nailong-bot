# 统一会话控制面板与 Magpie 模型接入规格

Based on #242

正式规格：[Issue #244](https://github.com/CxHsin/nailong-bot/issues/244)，标签 `ready-for-agent`。GitHub Issue 为权威版本，本文为本地归档。

2026-10-18，依据用户已确认的设计结论与 ADR-0016 整理。Magpie 端思考等级接口另由 #243 跟踪，不阻塞本规格。本文定义待实现行为，未声称功能已经完成。

## Problem Statement

用户已经使用 Magpie 管理供应商，却仍需为 Nailong 的每个主模型分别填写环境变量。新增模型不能自然出现在 Telegram，查看和切换模型还要等待当前处理轮次结束。手机上缺少统一的状态、模型、思考等级及工作操作入口，电脑上修改的模型与手机上的实际选择也缺少可靠回显。

用户希望在 Magpie 管理一次供应商，在 Telegram 随时看到当前可选模型；两边都能选当前助手的模型，Telegram 可以调整思考等级，切换时继续原来的上下文和工作，并看清实际生效状态。

## Solution

提供 Telegram 原生 Conversation Control Panel，由 `/start` 和对应快捷命令进入。面板展示当前状态，支持模型浏览、常用列表、思考等级、工作详情与操作、缓存统计、草稿预览及会话重置。

主助手只使用 Magpie 的 Model Catalog，通过 Magpie Agent 插件完成连接。模型菜单读取 Magpie 当前开放的目录，Telegram 和 Magpie 对当前 Telegram 主 Conversation 的最后一次明确修改生效，并回显同一选择。新设置不打断当前模型请求，在后续请求采用；暂停工作仍需明确继续。

偏好按 Conversation 持久保存。模型切换保留 Session、工作与已确认结果，能力不足或连接失败时提供明确状态和恢复操作。首版 Telegram 支持思考等级，Magpie 端等级控件延期。

## User Stories

1. 作为 Telegram 主人，我希望用 `/start` 打开统一面板，以便在手机上完成日常控制。
2. 作为 Telegram 主人，我希望首页显示实际模型、思考等级、运行状态和等待数量，以便理解助手目前在做什么。
3. 作为 Telegram 主人，我希望当前请求和工具运行时仍能查看面板，以便不必等长任务结束。
4. 作为熟悉命令的用户，我希望模型、缓存和会话操作的快捷入口继续可用，以便直接到达对应功能。
5. 作为 Magpie 用户，我希望只在 Magpie 管理供应商和账号，以便不用为 Nailong 重复配置凭据。
6. 作为 Magpie 用户，我希望通过 Agent 插件接入 Nailong，以便在 Magpie 的 Agent 页面看到并控制它。
7. 作为 Telegram 主人，我希望模型菜单列出 Magpie 当前开放的全部主模型，以便选到新接入的模型。
8. 作为 Telegram 主人，我希望刷新目录就能看到模型增删，以便不用逐个修改环境变量或重启 Nailong。
9. 作为 Telegram 主人，我希望模型按供应商和完整模型 ID 区分，以便同名或不同渠道的模型不会混淆。
10. 作为 Telegram 主人，我希望列表分页并标记当前模型，以便在较长目录中找到目标。
11. 作为 Telegram 主人，我希望点中模型就完成选择，以便减少频繁切换时的点击。
12. 作为 Telegram 主人，我希望另有详情入口展示模型已知能力，以便选择前了解窗口、图片和思考支持。
13. 作为 Telegram 主人，我希望有常用和全部两个范围，以便快速使用熟悉的模型而仍可浏览完整目录。
14. 作为 Telegram 主人，我希望能收藏和移除常用模型，以便自己维护常用范围。
15. 作为首次接入的用户，我希望系统让我选择模型，以便不因目录排序而意外使用某个模型。
16. 作为首次接入的用户，我希望尚未选模型时收到的消息得到保留，以便选择后继续原来的请求。
17. 作为桌面用户，我希望在 Magpie 修改 Nailong 的模型，以便不用拿起手机也能调整当前助手。
18. 作为 Telegram 主人，我希望手机上的模型选择回显到 Magpie，以便两边显示一致。
19. 作为双端用户，我希望最后一次明确修改决定当前模型，以便不会被旧设置反复覆盖。
20. 作为双端用户，我希望目录刷新、同步和重启不会改掉选择，以便模型只随我的操作改变。
21. 作为多 Conversation 用户，我希望 Magpie 只修改 Telegram 主 Conversation，以便 CLI 会话保持自己的选择。
22. 作为正在使用助手的用户，我希望切换不打断当前模型请求，以便保留已经产生的结果。
23. 作为正在使用助手的用户，我希望后续模型请求采用新选择，以便不用等待整个 Processing Turn。
24. 作为连续切换模型的用户，我希望最后一次选择生效，以便中间选择不会依次产生额外调用。
25. 作为 Telegram 主人，我希望面板区分实际请求设置和待生效设置，以便不会把已选择误认为已用于请求。
26. 作为 Telegram 主人，我希望按当前模型支持的等级调整思考，以便平衡速度和效果。
27. 作为 Telegram 主人，我希望每个模型记住它上次的思考等级，以便切回来不用重复调整。
28. 作为首次使用某模型的用户，我希望有一致的默认等级，以便可以直接开始工作。
29. 作为使用非推理模型的用户，我希望看不到无效等级选项，以便不会提交模型不支持的设置。
30. 作为已有会话的用户，我希望重启后模型、等级和常用列表保持，以便继续原来的使用习惯。
31. 作为切换模型的用户，我希望保留同一 Session 的上下文，以便新模型理解正在进行的工作。
32. 作为切换到较小窗口模型的用户，我希望优先使用既有压缩，以便尽量继续工作。
33. 作为上下文无法被新模型承接的用户，我希望获得暂停原因且记录保留，以便重新选择而不丢资料。
34. 作为暂停工作的用户，我希望换模型不会擅自恢复工作，以便恢复仍由我明确决定。
35. 作为暂停工作的用户，我希望点击继续后使用当前选择并复用已确认结果，以便无需重做已完成步骤。
36. 作为 Telegram 主人，我希望查看正在执行、排队、暂停和后台 helper 的工作，以便区分每项进度。
37. 作为 Telegram 主人，我希望工作详情对应真实 Work Target，以便不会把一个批次中的多个目标混为一谈。
38. 作为 Telegram 主人，我希望取消指定工作而保留其他目标，以便精准改变安排。
39. 作为 Telegram 主人，我希望停止中、已停止和待核实状态如实显示，以便不把发出中断请求误认为已经停止。
40. 作为 Telegram 主人，我希望独立请求继续遵循 FIFO，以便面板不会改变既有调度习惯。
41. 作为 Telegram 主人，我希望开关草稿预览，以便按自己的阅读习惯使用流式展示。
42. 作为 Telegram 主人，我希望关闭预览不影响最终回复和文件交付，以便控制展示时仍能收到成果。
43. 作为 Telegram 主人，我希望从面板查看已有缓存报表，以便了解实际模型请求的缓存情况。
44. 作为 Telegram 主人，我希望重置前知道影响并明确确认，以便避免误清上下文。
45. 作为 Telegram 主人，我希望 reset 保留队列、工作、helper 和设置，以便上下文重置不会取消事务。
46. 作为目录刷新失败的用户，我希望仍能看到上次列表和失败提示，以便知道只是刷新失败而不是模型全被删除。
47. 作为模型下架或调用失败的用户，我希望保留进度并能换模型和明确继续，以便恢复工作而不被静默切换。
48. 作为 Magpie 暂时不可用的用户，我希望面板仍能说明连接状态，以便修复连接而不必重建会话。
49. 作为 Bot 主人，我希望按钮执行与普通消息使用相同身份边界，以便其他用户或错误会话无法操作我的工作。
50. 作为旧配置用户，我希望升级保留会话和工作并给出清楚迁移提示，以便不再维护旧主模型配置的同时保留独立意图识别能力。

## Implementation Decisions

### 责任边界与入口

1. Assistant Service 提供统一控制查询和控制操作，Telegram 渲染、文本快捷命令和 Magpie 模型变更均调用此边界。复用现有 Queue System、Work Target、helper 控制和 Durable 执行器，不另建通用任务或权限框架。
2. 面板查询、模型与等级设置、草稿开关不进入普通用户工作队列，不调用主模型或意图识别模型。取消和继续转入已有对应执行路径；reset 仍在允许的上下文边界执行，按钮先说明影响并确认。所有操作保持 Conversation 归属。
3. `/start` 为统一首页，`/model` 进入模型选择；现有缓存、恢复、重置等入口调用同一能力。新的思考等级快捷入口进入同一设置页。旧 `/model` 文本参数可以识别完整 Magpie 模型 ID；旧静态别名无法识别时给出迁移或选择提示，不能把错误命令静默暂停。
4. 主页面包括模型、思考等级、工作列表、缓存统计、会话操作及草稿预览开关。子页面可返回首页；分页和收藏不产生模型请求。当前模型明确标记，空列表、无常用项、未连接及未选择都具有可理解的显示状态。
5. 按钮必须核对 owner、私聊、Conversation 和实际工作归属，并及时回答 callback。无效、过期或已经变化的工作按钮反馈当前事实，不执行猜测目标；重复投递不得重复恢复、取消或 reset。回调标识遵守 Telegram 长度限制，凭据和完整工作材料不塞入按钮。

### Magpie 连接、目录和请求契约

6. 提供可安装的 Magpie Agent 插件，声明 Nailong 的名称、检测方式及独立连接配置。首版只声明模型选择字段，不要求修改 Magpie 或增加等级字段。
7. 使用 Magpie 支持的 JSON 配置存储网关连接和 Telegram 主 Conversation 的共享模型引用；正式入口与插件共用稳定的配置定位规则，并提供单一连接配置路径覆盖入口。连接配置可在运行中重新加载，不借用基础指令、SELF、MEMORY 或逐模型环境项存储连接状态。
8. 插件写入只涉及其声明的连接与模型字段，保留其他配置；遵循 Magpie 原有断开恢复语义。Nailong 识别连接关闭后停止发起新的主请求，已有未知外部效果按现有规则处理，不自动转为直连。
9. 通过已配置网关认证调用 `GET /v1/models`；模型 ID 视为不透明完整标识，保留多层斜杠及路由组名称。请求原样发送目录 ID，不能按旧别名正则过滤或把供应商前缀丢掉。
10. 目录读取 `id`、`display_name`、`owned_by`、`reasoning`、`supported_reasoning_levels` 或 `reasoning_levels`，以及已知时的 `context_window`、`max_output_tokens`、`modalities`。以当前目录为选择依据；缺失能力标为未知，不凭名称伪造支持等级、图片能力或模型规格。
11. 首次连接、打开模型页和显式刷新可获得更新目录；重复翻页复用当前目录快照，不按每个按钮查询所有供应商。刷新有界，失败保留上次成功目录并展示失败状态，不把失败当作成功空目录。
12. 当前模型在成功刷新中被确认移除时，保留选择和工作，标记不可用并要求重新选择；失败时的陈旧目录与成功返回的移除必须区分。收藏只保存模型引用，模型不可用时不能绕过目录校验。
13. 主执行使用现有 pi-ai 与 Durable 请求链，经 Magpie 已支持的协议调用，保留流式、工具、图片及 reasoning 参数。协议编码继续由 provider 适配层负责；不得因换协议丢失已确认工具结果。网关记录使用 Nailong 专属客户端身份，连接凭据不出现在菜单或诊断正文。
14. 统一目录不等于逐模型验证可调用：列表可用与实际请求成功分别记录。网关本身提供的路由组可以原样选择，Nailong 不在其上增加自行换模型或跨供应商故障转移。

### 模型归属、双向同步与持久状态

15. 持久设置以 Conversation 为主键，至少保存期望模型、各模型思考偏好、常用模型和草稿开关；保留现有会话数据库、队列和 Durable 数据，不启用新空白执行空间来规避迁移。
16. Magpie 共享模型字段只绑定 owner 的 Telegram 主 Conversation；其他 Conversation 使用自己的持久选择，同样从 Magpie 目录选择，不把 Magpie 的单个桌面选择广播给所有会话。
17. 模型在共享配置中的引用形式须与 Magpie 菜单选项一致。可利用既有插件 `prefix` 将网关模型 ID 与 Magpie 客户端引用分开；真正发请求时仅去除约定增加的一层客户端前缀，目录 ID 本身保持不变。回显须通过实际 Magpie 验收。
18. Telegram 选择先校验当前模型引用，序列化保存并回写共享字段；Magpie 改模型由同一服务控制路径接收。两边最后一次明确修改胜出；判断依据是已观测到的模型字段变化与本次回写记录，不能仅因文件时间戳、重新读取或目录同步而重放旧值。
19. 共享配置加载和局部写入必须保留较新的模型字段及未知配置项，不用过时的整份快照覆盖另一个写入者。未完成或无效配置读取不得清空有效状态；明确反馈连接配置异常，之后可重新读取。实现采用满足本机单服务责任的直接协调方式，不引入跨进程事务平台。
20. 程序重启从持久记录恢复选择，并核对共享配置中的实际变化；不重新应用默认模型。首次没有有效已保存或明确指定的选择时，控制面板和普通输入接收仍可工作，普通输入持久等待选择，不启动目录第一项或旧默认别名。
21. Magpie 目录同步、连接重载、Telegram 回写回声和模型能力变化均不能被视为另一次用户模型选择。缺失或不再有效的保存值需要用户重新选择，不静默切成任意候选。

### 请求边界与思考等级

22. 将“期望设置”和“实际请求设置”分开展示。请求在准备阶段冻结模型与等级，已准备或发出的请求保持原参数；新选择提交后开始准备的下一主请求使用新参数。若用户在请求进行中选择 B 后又选 C，当前请求继续，下一次准备只采用 C。
23. 空闲且无已冻结请求时可立即更新生效状态；工具执行期间允许更新设置，工具本身继续并保留结果，之后主请求采用最新选择。设置变更本身不创建用户工作、继续提示或额外生成。
24. 主生成的临时失败重试使用现有有限预算，不因切换重置计数，也不叠加 provider 重试。下一次重新准备可采用最新模型；已准备的压缩请求及其重试沿用冻结参数，不因切换重复已完成步骤。
25. Telegram 的等级选项仅来自目录明确提供的支持集合。首次优先 medium，其次 low，再选支持的最低等级；不支持推理时使用非推理行为并隐藏入口。声明推理但未提供等级集合时显示能力未提供，不编造可调档位，调用不强行发送猜测的 effort。
26. 等级按完整模型引用分别保存。选择模型时恢复仍受支持的偏好；若能力更新使保存等级失效，按首次规则选择受支持等级并在页面说明调整，绝不向网关发送已知不支持的值。Magpie 换模型采用同一偏好规则，不覆写其余模型的偏好。
27. 等级调整使用与模型选择相同的请求边界。Magpie 不提供等级控件也不会在目录同步时重置 Telegram 已保存等级。

### 工作、上下文与展示

28. 换模型继续原 Session，保留 MEMORY/SELF 快照、历史、归档、队列、Work Target 和 helper 身份。较小窗口沿用既有原生容量检查与压缩；仍无法承接时暂停说明，保留原始材料，不自动 reset 或静默删除图片、工具结果和用户消息。
29. 暂停工作中只改变模型或等级不会发起请求，也不会解除未知外部效果的核实要求。用户明确继续后采用当前选择并复用已确认成果；首次未选择模型的等待输入在选择完成后按原 FIFO 推进，与已暂停工作区别处理。
30. 工作详情和操作基于真实 Work Target，不能用 Processing Turn 完成标记证明用户目标或 helper 已完成。排队、执行中、暂停和后台工作分别展示；同批多个目标可以独立取消，其他目标保留。
31. 取消和继续复用现有 Queue System、Routing Action 和 helper 控制语义，不通过额外自然语言模型推测按钮目标。取消后按真实结果显示停止中、已停止或待核实；重启、reset 和 resume 不使已取消目标复活。
32. reset 保留模型、各模型等级、常用列表、草稿开关及所有现有执行记录，仍只重置上下文。面板确认与实际重置结果分别反馈，不把收到按钮当作已经重置。
33. 草稿开关按 Conversation 保存，首次保持现有开启行为。关闭后停止后续草稿更新，不承诺撤回已发送预览；最终文本、文件、Send Receipt 及错误交付流程继续正常。重新开启只恢复合法的后续预览。
34. 缓存入口直接复用现有 `/kvcache` 统计，仍以实际主模型请求分组，不把菜单、刷新、目录或独立分类调用算作 Processing Turn 请求。
35. 模型移除、目录故障、请求重试耗尽和连接关闭均提供可见恢复入口。重试耗尽保留现有 Paused Work；面板的换模型与继续是两个动作。明确拒绝、未知发送和工具外部效果继续沿用已有记录，不新增自动重复发送。

### 配置迁移与交付

36. 正式 Telegram/CLI 启动不再要求旧主模型别名及默认值才能打开控制入口；主助手模型只从 Magpie 目录产生。拆开主模型接入与独立意图识别配置加载，保留后者现有校验、凭据与降级职责。
37. 升级时保留全部现役 Conversation、队列、取消标记、helper 和已确认 Durable 步骤。旧主模型引用不能精确匹配新目录时保留进度、提示重新选择；不能猜测映射或继续以旧直连作为隐藏后备。未确认的旧请求按既有恢复边界核对，不能整轮重跑。
38. 现有普通输入、自然语言补充/取消、CLI 会话选择、系统指令和记忆职责保持。更新当前启动与操作说明、命令注册、配置示例、ADR 实现状态和迁移提示，清理主模型旧入口的实际调用方；历史验收保留日期和基准。
39. 交付包括 Nailong 功能、Agent 插件、正式入口配置说明、自动化行为测试及真实 Magpie/Telegram 验收记录；不以模拟网关通过代替真实插件回显已验证。

## Testing Decisions

### 主要测试入口

采用一个组合式最高层行为入口：扩展现有 `assistantFixture` 和 `telegramFixture`，用真实 `createAssistant`、`connectTelegram`、grammY `Bot.handleUpdate()`、Queue System、SQLite 和 Pi Durable。由真实 Telegram 消息/callback 及 Magpie 配置变化驱动，检查 Telegram 输出、模型 HTTP 请求、配置回写与重启后的持久事实。

只替换进程外依赖：现有 Telegram Bot API fetch、现有本地 HTTP 模型服务器，以及可控 Magpie 目录/配置读写。扩展外部替身支持目录和请求端点，使用真实连接配置编解码；不逐层 mock Service、队列、executor 或 SQLite。受控模型和工具用 Promise 闸门确定请求边界，不靠固定 sleep 猜测时序。重启测试须重建 Telegram channel 并连接新的 Assistant Service。

好测试验证用户可见结果、实际请求和外部效果；不以内部函数调用次数、私有数据结构或复制实现逻辑作为主要证据。菜单快照只能作为辅助，不能证明切换实际生效。现有测试先例包括实时 `/kvcache` 查询、四次请求失败后暂停与明确 resume、指定目标取消跨重启保持、正式 CLI 独占与恢复。

### 必须覆盖的行为矩阵

1. **无模型首次接入**：不提供旧主模型配置也能打开面板；普通输入持久等待、不发主请求；重启后仍保留；明确选定后按 FIFO 推进。
2. **动态目录**：新增、删除、路由组、多层斜杠 ID、分页、当前项、详情和常用列表可见；刷新后可选项更新，已删除项不再触发有效切换。
3. **刷新故障**：超时、拒绝或无效目录不清空成功快照；显示失败并可重试；成功空目录与失败有区别。
4. **双端选择**：Telegram 选择写入实际配置并被 Magpie 读回；外部模型修改在 Telegram 回显；最后一次明确选择胜出；CLI 等其他 Conversation 不随之改变。
5. **同步与重启**：目录同步、配置重读、回写回声和重启不产生旧模型覆盖或额外请求；交错局部写入保留较新的模型和其他配置项。
6. **请求中切换**：挂住 A 请求，连续选择 B/C，立即看到实际 A 和待生效 C；A 不被中止；后续真实网关请求的 model 为 C，B 不产生独立调用。
7. **工具与重试边界**：工具挂起时仍能查询和设置；效果文件只写一次，下一主请求采用最新模型和等级；失败后的重新准备使用最新设置且不重置有限重试预算。
8. **思考偏好**：覆盖 medium、low、最低等级、非推理、未知等级集合和能力更新；核对实际请求参数，切回、reset 与重启恢复正确偏好，不发送不支持的等级。
9. **暂停恢复**：耗尽后只通知一次；暂停时换模型/等级不发请求；明确继续采用当前值；已确认工具成果复用，未知外部效果不被菜单绕过。
10. **上下文衔接**：切换后实际请求保留原用户目标和工具结果；较小窗口触发现有压缩；无法承接时暂停保留记录，不自动 reset 或静默移除资料。
11. **工作列表控制**：详情匹配真实 Work Target；排队、执行中与 helper 取消只影响目标，其他目标继续 FIFO；停止事实准确，跨 reset/reopen/resume 不复活。
12. **callback 边界**：非 owner、非私聊、错误 Conversation/work 及过期标识不能操作；合法重复投递不会重复副作用；所有失败有可见反馈。
13. **面板独立性**：模型/工具挂起期间面板、翻页、收藏、草稿开关和缓存查询正常，无额外主模型或分类请求，不形成普通工作队列项。
14. **草稿与最终交付**：开关跨重启保存，关闭不再更新草稿，但最终文本、文件及发送回执仍正常；预览不作为已发送成果。
15. **reset**：先说明并确认，取消确认不清上下文；实际 reset 保留工作、helper、模型及偏好，不间接恢复暂停工作。
16. **迁移与正式入口**：现役数据不清空，旧引用需明确重选，不启动隐藏直连；独立 intent 配置仍正常，缺失或非法 intent 配置按原规则处理；正式 CLI 保持独占与会话选择语义。
17. **实际链路验收**：用用户安装的 Magpie 和 Telegram 手机验证插件安装、模型双向回显、刷新不覆盖、忙时切换、等级调整、重启与断连恢复。记录实际版本、请求证据、模型与测试数量；模拟通过而真实项未完成时明确保留缺口。

实现完成后运行项目要求的类型检查、受影响行为测试、全仓回归、构建及文档检查，记录实际结果与条数。规格编写阶段只做文档检查，不将未来测试列作已通过。
