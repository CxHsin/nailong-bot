# 事件队列系统与持久工作流讨论

日期：2026-10-15。状态：行为与技术选型已确认；剩余规格与迁移验收待完善，亦不表示现有运行时已实现。

用户先同意做 Pi Durable 接入验证；[实际验证报告](pi-durable-integration-2026-10-15.md)记录 9 项通过、适配成本与验证边界。澄清在用工具与闲置扩展参数后，用户确认更新方案：采用 Pi Durable 承载主 agent 持久执行，nailong 自有队列负责路由、去重、优先级与 FIFO，见 [ADR-0011](../adr/0011-durable-main-agent-and-conversation-queue.md)。以下约定是已接受的目标行为，正式入口尚未切换。

## 问题与当前基线

用户本次关注的是外部事件进入主 agent 前的队列系统，以及主 agent 执行过程中的持久工作流。它不是对旧 Host 的通用 Task/Attempt、权限或结算协议的恢复。

[ADR-0010](../adr/0010-native-pi-assistant.md) 与[规格 #196](https://github.com/CxHsin/nailong-bot/issues/196)使用原生 Pi Session 和薄接入服务，明确暂缓了通用持久工作流。当前 `inputs.json` 先记录输入身份再执行，不能保证崩溃后继续尚未完成的输入；会话 JSONL 和帮手观察也不能证明主 agent 的每个工具操作均可恢复。

本次确认重新讨论上述恢复范围。此前[记忆讨论](persistence-memory-decisions-2026-10-15.md)中的“重启后先汇报并等待继续”被本次“自动恢复”决定替代；其余记忆问题继续保留在原讨论中。

## 已确认的链路与范围

事件进入路由层，由路由层去重并选择会话，再进入会话队列，最后由主 agent 处理。路由层和会话队列合称“队列系统”。持久工作流保存主 agent 的执行进度，以应对网络、基础设施故障、进程中断和重启。

第一版面向当前 Windows 本机、单个 bot 服务。用户输入是当前事件来源；cron、邮件、群聊和 Slack 线程等是将来的来源，本次不实现这些连接器。第五章仅用于指导恢复材料的保存与呈现；完整分层记忆和缓存优化不属于本次范围。

## 已确认的队列行为

- 每个会话一次处理一个主 agent 轮次；轮次与整个用户目标的生命周期分开。
- 根据事件优先级决定是否抢占。直接用户输入高于后台来源；更高优先级可以打断较低优先级处理。同优先级按进入顺序排队，后来发来的直接用户输入不会仅因更晚到达就抢占当前直接用户输入。
- 当前轮结束或会话空闲时，批量读取当时已经排队的连续普通消息，不为凑批主动等待。在同会话、同来源、同优先级范围内按原顺序交给下一轮，保留每条原始消息的身份、正文与边界，不假定它们属于同一业务目标。命令和不同优先级构成合批屏障。
- 用户不接受用固定时间窗决定普通消息合并；此前提出的 800 ms 建议已撤回。[一手资料调研](personal-agent-message-scheduling-2026-10-15.md)后，用户确认上述轮次边界合批，并进一步明确 Telegram 通过 `/steer 内容` 才使用运行中补充。普通新消息继续排队，不自动改为 steer。
- `/steer` 是显式补充当前工作的控制入口，在下一个可接收输入的执行边界加入。该边界前已接收的连续 `/steer` 可以按序一起读取，各条内容和身份保留；不使用等待时间窗，也不意味着立刻终止正在运行的模型或工具。如果模型已给出最终答复，Durable 可能将待处理 steer 放进后续 run，不能承诺总在原 run 内消费。
- 空闲时 `/steer 内容` 去掉命令前缀后作为普通消息入队，遵守已有队列顺序；空的 `/steer` 只显示用法。
- 被抢占的工作保留已完成进度。高优先级轮次结束后，主 agent 结合最新指令检查是否仍需继续；需要则复用结果，发生冲突则调整或结束，不能机械恢复旧计划。
- 主 agent 派发 herdr 并结束本轮后，允许处理队列中的后续输入，不等待外部帮手完成整个工作。

## 主 agent 与 herdr 的分工

主 agent 保留用户目标、关键约束、结论和待办。herdr 帮手在独立上下文中执行命令、浏览器操作等工作，将结果摘要和证据位置交回主 agent；中间执行轨迹保留在帮手侧，需要时再查证。

herdr 回传属于内部执行材料，不变成用户消息，也不因回传本身直接发送到 Telegram。本次不要求把它当成外部事件放入用户输入队列。内部结果如何在主 agent 可接收时交付，属于执行协调；主 agent 仍需检查实际成果，不能以 idle/done 代替验收。

本次保存委派身份、目标和返回结果；主服务重启后查询原来的 herdr 执行并接回成果，不盲目重新派发。本次不改造 herdr 内部，使其获得自身每个工具步骤的恢复能力。

## 已确认的恢复与错误处理

- 主 agent 保存模型和工具操作的进度与已确认结果。恢复时复用已完成成果，从中断处继续；不能只保存事件再从头运行，也不能只恢复待办摘要。
- 临时网络或基础设施故障自动有限重试。工具或业务错误交回主 agent 判断并修正，不把所有错误统一机械重试。
- 用户确认模型临时故障重试耗尽后保留执行进度，暂停该项工作并通知一次，等待明确继续指令；其他可处理输入继续推进。重试由执行器一层负责，底层不叠加重复重试，应用队列不重跑整个轮次来重试模型请求。重启保留已暂停状态，不将它误当作意外中断而自动续跑。
- 进程重启后自动恢复排队事件和执行进度，无需每次先取得继续指令。
- 操作可能已生效但结果尚未确认时，先核实外部实际状态。确认完成则采用结果，确认未执行才执行；无法确认则暂停该操作并询问用户。
- 打断或取消不撤回已发生的外部效果。
- `/reset` 只重置主 agent 会话上下文，保留已接收事件、执行进度和 herdr 委派；继续时加载必要材料。取消工作另由明确的取消请求处理。

## 已确认的技术取舍

选用 Pi Durable 承载主 agent 的持久执行；nailong 自有持久队列负责路由、去重、会话选择、优先级、同级 FIFO 与合批。当前 Pi SDK 的原生 steering 不会立刻停止正在运行的工具，会话 JSONL 也没有完整工具 intent/result 恢复协议；不能仅凭现有 Session 持久化声称满足上述行为。

选择依据是本机已验证模型、技能、工具恢复和 herdr 接入路径；相较 Temporal，无需增加独立 Service/Worker；相较在旧 SDK 上自建完整工具恢复协议，可复用 Durable 的持久执行能力。代价是新的 Harness 接口、会话衔接和应用队列交接仍需实现。保留 `herdr_watch` 与 `send_file` 能力，迁移后删除被替代的旧注册实现；没有使用者的接口删除。当前核查未发现第三方扩展依赖，无需建设通用旧扩展兼容层；详见[接入报告中的清理说明](pi-durable-integration-2026-10-15.md#当前工具与扩展清理)。

应用队列保留全部未运行普通事件，仅将选中的当前批次提交给 Harness；显式 `/steer` 另按控制语义提交。不能将整个普通队列预先交给 Durable inbox，因为 abort 会撤销其中的等待输入。`/steer` 原始内容与提交身份也需持久保存；中断后核对其是否已被消费，不能丢弃或重复注入。被抢占事件保留原身份和进度；后续用新的 submission 关联原事件，结合最新指令续接，而不是重用已 aborted 的 requestId。

最初只读核对的事实如下；之后的安装与运行结果见上述实际验证报告：

- [Pi Durable 官方源码](https://github.com/earendil-works/pi/tree/6a1f799b675c8cb98320b71ff7ee44f160fe8d66/packages/durable)与 [npm metadata](https://registry.npmjs.org/@earendil-works/pi-durable/latest)均显示版本 1.2.0，但没有逐文件比对源码与发布包。README 仍标记 Experimental；它使用独立 Harness，已有模型/工具持久 task、intent/result 和 safe/unsafe 重放策略。没有找到直接导入当前 coding-agent 扩展、ResourceLoader 或旧 Session JSONL 的官方接口；优先级与保留队列的抢占也仍需适配。
- Durable 要求 Node >=22.19，使用 `node:sqlite`；官方 Node 执行环境包含 Windows Git Bash 与进程树取消处理。这是源码支持证据，不是本机集成已通过的证据。
- [Temporal Activity 官方说明](https://github.com/temporalio/documentation/blob/cdc231e55d811d8d0df5b75b38dd2546b2131e2f/docs/encyclopedia/activities/activity-definition.mdx#L188)表明 Activity 返回前的内部步骤不形成独立恢复历史。仅把整个 Pi `prompt()` 包成一个 Activity，不能获得其中每个工具步骤的恢复；还需暴露工具步骤或增加工具账本。它另需运行 Service 与 Worker。
- 保留当前 Pi SDK 的方案可继续使用现有 Session、技能和扩展，但需自行补齐持久输入、工具 intent/result、成果复用、未决操作核实与恢复衔接；当前 SDK 的事件 hook 不是现成恢复执行器。

## 剩余规格与迁移验收

用户确认切换时丢弃旧会话历史，不导入旧摘要、近期对话或详细工具记录，新会话从空白上下文开始。这里规定的是新运行时不加载旧历史，不据此扩大为删除本地目录、凭据或成果文件；委派身份与已发生外部效果也不能由旧上下文缺席推导为不存在。

轮次边界合批、Telegram 显式 `/steer`、空闲 steer 转普通输入、重试耗尽后暂停保留进度及旧会话历史不迁移均已确认。规格仍需明确批次与原始事件的完成/取消/恢复关系、答复组织、路由匹配与去重键、内部结果交付时机、重试数值上限，以及切换数据空间的办法。这些细节不能因执行引擎选定而视为已经确认。

以下是正式接入的验收要求，不是现有实验已覆盖的保证：

- 重复输入在重启前后仍只形成一个待处理事件；接收成功后即崩溃，输入正文和队列位置仍可恢复。
- 同会话单轮串行、同级 FIFO；直接输入抢占后台事件，同级新输入不抢占当前轮次。合批保留原事件身份，不改变顺序，也不跨优先级混合。
- A 处理期间收到普通输入 B、C 时，B、C 不自动注入 A；A 结束后按当时的有限队列快照交给下一轮。取快照后再到达的 D 留待后续，命令或不同优先级隔开批次；重启不能丢失原始消息身份或把它们当新输入重复接收。
- 显式 `/steer` 在可接收输入边界按序加入，边界前连续收到多条时均可见且保留身份。普通输入不混入 steer 队列；覆盖工具执行中到达、模型最终答复时到达，以及重启/abort 交接，防止丢失补充或同一条补充进入当前与后续轮次两次。
- 在应用队列领取事件、提交 Harness、保存 submission、记录完成与确认队列结果的交接处分别强杀；重开后事件不丢，已确认工具结果不因交接重做。
- 抢占后核对最新指令，分别覆盖继续、调整与结束旧工作；任意 Shell 不一概标为 safe，外部效果不明时先核实，无法核实则暂停询问。
- 主 agent 派发 herdr 并结束本轮后可处理后续输入；重启查询原帮手身份、接回摘要与证据，内部结果去重，不混入外部用户输入队列。
- 临时基础设施错误有限重试，工具/业务错误交回模型；重试耗尽及未决效果有可恢复状态，不能无声丢弃。
- `/reset` 清理主上下文后，待处理事件、执行进度和委派仍在；继续时加载必要材料。明确取消与重置分开，均不能声称撤回已发生效果。
- Telegram 与 CLI 继续支持实际模型配置、项目指令/技能、图片输入、`send_file`、草稿和回执；未知发送结果不自动重发。按选定的历史衔接方案验收旧会话与新执行空间。

实验只在已保存抢占状态的位置强杀，未覆盖上述所有交接窗口；真实 herdr 项验证的是已完成结果接回。应将这些缺口纳入迁移验收，不扩写为现有保证。
