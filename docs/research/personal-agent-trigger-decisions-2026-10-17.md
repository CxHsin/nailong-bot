## 创建、执行与通知

2026-10-18，用户同意上一轮 Q9–Q11 的推荐，并补充服务未启动时的到期消息处理规则。

- 定时任务以自然语言对话为主要创建和管理入口，支持修改、暂停和查询。时间、执行内容及通知条件明确时直接创建，并回告实际保存的安排；有歧义时追问。默认沿用用户设置的时区，支持显式指定其他时区。
- 后台任务按主人定义任务时授予的范围自动执行。检查与报告不自动扩大成修复或对外操作；明确授权修复的任务可在范围内执行，并遵循项目已有的提交和发布规则。需要扩大范围时，向主人提出具体请求。
- 邮件正文、附件与网页内容是外部资料，不能自行扩大主人授予的权限。
- 一次性提醒到期通知；周期检查没有值得关注的变化时保存结果、保持安静；重要变化或需要主人介入的问题及时通知。普通进展默认合并为每日摘要，单项任务可另设条件。临时故障沿用已有重试规则，最终影响完成时再告知，避免重复报错。
- 用户明确要求：到发送时间时服务若未启动，消息不得丢失，启动后进入待发送队列补发。实现须持久保存足以识别到期发送的安排；服务离线时不能依赖内存定时器或一个仍在运行的进程即时入队。启动后补入遗漏的待发送项。

## 调度合并、通知目的地与邮件起点

2026-10-18，用户同意 Q12–Q14 的推荐；邮箱提供方尚在 Gmail 与 QQ 邮箱之间比较。

- 周期检查停机错过多次时，启动后合并为一次检查，覆盖自上次成功检查以来的变化。同一任务上一次仍在运行时，最多保留一次待检查，不积压每个时间点的独立执行，也不并发启动同一任务。
- 一次性提醒逐项补发，保留各自内容和原定提醒时间，不采用周期检查的合并规则。
- 普通私聊回复当前入口。主动提醒、邮件通知和后台结果默认发 Telegram；创建任务时可指定其他已接入渠道，避免默认重复发送至多个入口。
- 每日摘要默认在 `Asia/Shanghai` 的 21:00 发送，无内容时不发；离线错过发送时间则启动后补发。
- 邮件首批接一个邮箱，从启用接入后收到的新邮件开始处理。历史邮件仅在主人明确要求检索或整理时读取。用户询问 Gmail 与 QQ 邮箱哪个更易接入，以及是否必须使用 MCP；尚未选择提供方或协议。

## 当前基线

- [CONTEXT.md](../../CONTEXT.md)区分 Input Event、Channel、Conversation 和 Queue System。
- [ADR-0011](../adr/0011-durable-main-agent-and-conversation-queue.md)已有直接用户输入高于后台输入、同级 FIFO、已有输入合批和持久执行恢复的设计。
- [ADR-0013](../adr/0013-contextual-input-routing.md)定义现役上下文意图路由；用户补充不依赖已退役的 `/steer` 入口。
- 当前队列已支持同一 Conversation 内的优先级抢占，不能将其描述为跨会话全局抢占或外部工具立即停止。Telegram 当前仅接收主人私聊；cron、邮件和 QQ 尚无现役连接器。
- 2026-10-18 核对发现，现有应用输出表仅保存 ID 与发送状态，不保存完整待发内容和目的地，也没有启动补投扫描。执行恢复不等于消息补投；本轮需要补足明确未发送消息的持久保留与投递恢复。现行 Send Receipt 对未知发送不自动重试的规则保留，用户的离线补发要求没有改为未知发送盲目重试。
- 当前 MCP 集成支持 stdio 与 HTTP Streamable 工具调用，启动时列出工具供 Agent 使用；没有 MCP 通知、资源订阅转 Input Event 的路径。仅配置邮件 MCP 不会自动提供新邮件触发。邮件同步监听与模型按需查信是不同职责，具体适配方式待选择。
