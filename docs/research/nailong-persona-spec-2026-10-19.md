# Telegram 奶龙交互、全局路由模型选择与启动招呼规格

Based on #259

正式规格：[Issue #260](https://github.com/CxHsin/nailong-bot/issues/260)，标签 `ready-for-agent`。

2026-10-19，依据已确认讨论编写。GitHub Issue 为权威规格，本文为本地归档；规格描述待实现行为，不代表功能已完成或服务已部署。

## Problem Statement

用户希望私人助手在 Telegram 中有自然、鲜明的奶龙性格，并能通过贴纸、消息表情回应和投喂互动获得陪伴感。现有助手已有基础人设和回复草稿，但缺少这些原生互动，等待阶段的表达也尚未与真实执行状态协调。

用户还需要在手机上直接调整表达频率、查看饱食状态、打开缓存详情，以及独立选择路由模型。当前缓存详情按钮藏在设置页，路由模型固定在启动配置中，无法通过控制面板调整。服务启动后缺少明确的上线消息，也没有一条实际模型生成结果让用户判断主模型是否可以调用。

用户希望上述能力建立在可靠工作之上：无需投喂才能办事，角色表达不替代事实，切换设置不丢进度，重启不重复执行已确认的工作。

## Solution

扩展现有 Conversation Control Panel 和 Telegram Channel，提供奶龙贴纸、消息表情回应、四档主动表达频率，以及只影响角色表现的 Satiety。以真实事件呈现等待状态，在生成正文后衔接现有草稿预览。

`/start` 首页直接提供缓存详情入口、饱食状态和投喂按钮，并提供标注作用范围的全局 Routing Model 选择入口。主模型与路由模型共用 Magpie Model Catalog，分别保存选择；前者沿用 Conversation 归属，后者由整个 Assistant Service 共用。

每次 Telegram 服务启动后，使用当前主 Conversation 所选主模型实际生成一句奶龙上线招呼，给主人私聊发送。该短请求同时验证模型调用，独立于用户工作和主 Session 的任务历史；失败时准确报告，不妨碍控制面板和接收输入。

## User Stories

1. 作为 Telegram 主人，我希望奶龙保持贪吃、可爱且自然的表达，以便日常交流更有陪伴感。
2. 作为交办任务的用户，我希望奶龙始终认真可靠，以便角色表现不会降低办事质量。
3. 作为要求精确输出的用户，我希望代码、路径、引用和结构化结果保持原样，以便直接使用结果。
4. 作为处理紧急事务的用户，我希望奶龙收敛装饰性表达，以便迅速理解结果和错误。
5. 作为 Telegram 主人，我希望奶龙在合适的语境发送贴纸，以便交流更生动。
6. 作为 Telegram 主人，我希望奶龙能对我的消息点表情，以便获得轻量回应。
7. 作为贴纸使用者，我希望可以指定贴纸包或明确收录单张贴纸，以便奶龙使用我喜欢的素材。
8. 作为贴纸使用者，我希望普通发送或转述贴纸不自动授权收录，以便素材库符合我的明确选择。
9. 作为 Telegram 主人，我希望奶龙从已收录素材中选择，以便表现符合我的偏好。
10. 作为尚未准备贴纸素材的用户，我希望其他功能仍可使用，以便不被素材准备阻塞。
11. 作为 Telegram 主人，我希望在设置页调整主动表达频率，以便适应不同场合。
12. 作为偏好清静的用户，我希望安静档不主动发贴纸或点表情，以便减少消息干扰。
13. 作为选择安静档的用户，我希望明确要求贴纸或回应时仍能使用，以便保留主动互动能力。
14. 作为 Telegram 主人，我希望有克制、自然活跃和热闹档，以便选择不同的活泼程度。
15. 作为初次使用者，我希望默认自然活跃、工作时适当收敛，以便开箱就有奶龙性格。
16. 作为正在交办任务的用户，我希望调整频率不打断工作，以便随时改变偏好。
17. 作为重启服务的用户，我希望表达设置保留，以便不用反复设置。
18. 作为喜欢养成互动的用户，我希望奶龙有随时间变化的饱食度，以便感到持续相处。
19. 作为 Telegram 主人，我希望首页显示饱食状态并能查看数值，以便知道奶龙现在的食欲。
20. 作为 Telegram 主人，我希望通过自然语言、`/feed` 或投喂按钮喂食，以便选择方便的互动方式。
21. 作为聊天用户，我希望只在明确投喂时增加饱食度，以便讨论食物、引用文章或发送食谱不会被误当成喂食。
22. 作为 Telegram 主人，我希望同一次投喂不会因重复更新或重启重复生效，以便状态可信。
23. 作为离线几天的用户，我希望时间流逝仍反映在饱食度中，以便养成状态连续。
24. 作为重置上下文的用户，我希望饱食度保留，以便会话维护不抹掉养成状态。
25. 作为忙碌的用户，我希望饥饿不限制工作，也不主动发消息催喂，以便无需承担照料负担。
26. 作为等待结果的用户，我希望先看到符合真实状态的奶龙提示，以便知道请求处于什么阶段。
27. 作为等待结果的用户，我希望有正文后看到实际草稿，以便及时阅读有效内容。
28. 作为需要判断进展的用户，我希望奶龙不把固定动画或一轮模型结束说成目标完成，以便正确判断工作状态。
29. 作为习惯现有命令的用户，我希望原命令及其行为继续可用，以便不重新学习控制方式。
30. 作为 Telegram 主人，我希望首页直接有缓存统计按钮，以便少走一层菜单。
31. 作为查看用量的用户，我希望首页摘要、最近五轮详情和 `/kvcache` 保留原统计口径，以便继续比较实际用量。
32. 作为 Telegram 主人，我希望 `/start`、缓存查询和投喂按钮无需模型生成，以便在主模型故障时仍可操作。
33. 作为 Telegram 主人，我希望能独立选择路由模型，以便为输入意图判断选择合适的模型。
34. 作为模型管理者，我希望主模型和路由模型共用 Magpie 目录，以便统一管理供应商和可用模型。
35. 作为模型管理者，我希望两类模型分别保存选择，以便切换其中一个不改变另一个。
36. 作为使用多个 Conversation 的用户，我希望面板明确路由选择是全局的，以便理解它影响整个助手服务。
37. 作为正在聊天的用户，我希望路由切换从下一次判断生效，以便当前判断不中断、已有判断不重跑。
38. 作为重启服务的用户，我希望全局路由选择保留，以便继续使用已选模型。
39. 作为遇到路由故障的用户，我希望原消息仍交给主助手处理，以便分类失败不会吞掉输入。
40. 作为升级现有服务的用户，我希望已有队列、工作和模型选择保留，并能看清尚未配置的新路由选择，以便安全继续使用。
41. 作为 Telegram 主人，我希望服务每次启动后发送一句模型生成的奶龙招呼，以便知道奶龙上线且模型能返回内容。
42. 作为模型管理者，我希望启动测试实际使用当前所选主模型，以便测试结果对应真实配置。
43. 作为 Telegram 主人，我希望无模型、调用失败或超时时收到如实说明，以便区分服务在线和模型可用。
44. 作为有暂停工作的用户，我希望启动招呼不恢复或修改工作，以便重启不替我作出继续决定。
45. 作为网络偶有波动的用户，我希望普通重连不重复发上线消息，以便避免重复通知。
46. 作为查看费用与诊断的用户，我希望启动测试的模型、耗时、结果和真实 usage 可追溯，以便核对调用成本和故障。
47. 作为交办重要工作的用户，我希望贴纸、回应或等待提示失败时，正式结果仍能正常交付，以便装饰性能力不妨碍工作。
48. 作为 Telegram 主人，我希望所有新增按钮和互动沿用私聊鉴权及重复操作保护，以便只有我能修改助手状态。
49. 作为查看失败结果的用户，我希望发送结果未知时不会自动重复发送，以便避免重复消息或副作用。
50. 作为完成部署验收的用户，我希望分别看到自动化测试和真实 Telegram、Magpie 验收证据，以便知道哪些行为已经实际验证。

## Implementation Decisions

### 1. 职责与现有保证

- 在现有 Assistant Service、Channel、Queue System 和 Durable Workflow 内完成接入，不新建独立宠物服务、调度框架或第二套会话历史。
- Persona Expression 沿用 SELF 的身份、相处原则和表达边界。保持基础指令、skills、项目指令、SELF 和 MEMORY 的现有次序与快照职责，不通过养成状态改写身份或长期记忆。
- 等待状态、饱食度和当前表达档位是当前运行材料；按需要追加，不因时间变化每秒改写稳定系统前缀。
- 主模型负责回复与工作，Routing Model 负责理解 Input Intent 和提出 Routing Actions；实际队列和工作事实决定动作能否执行。
- 保留鉴权、输入持久接收、去重、同级 FIFO、Work Supplement、暂停/恢复、未知外部效果核实、helper 身份以及发送回执的现有保证。

### 2. 面板和控制接口

- 扩展现有控制快照和动作，表达可查询、可修改的频率、饱食状态、投喂和全局路由选择。Telegram 面板只调用服务接口，不直接操作存储或绕过服务更改模型。
- 首页保留现有实际状态、Token/Cache/Context 摘要、主模型、思考等级、工作和设置入口；新增饱食状态入口、投喂按钮和全局路由模型入口。
- 将现有缓存详情按钮从设置页移到首页；详情页能直接返回首页，仍提供最近五轮报告，`/kvcache` 继续可用。
- 设置页提供四档表达频率及现有草稿和会话操作。表达频率与草稿开关分别保存；关闭草稿时不另开等待预览来绕过该开关。
- 原生命令/按钮不等待整个 Processing Turn，不通过主模型解释点击，不因启动招呼尚未完成而无法使用。
- `/start` 和缓存查询本身不调用模型。`/feed` 和投喂按钮直接提交有身份的控制动作；自然语言投喂仍属于普通用户交流。
- 保留 `/reset`、`/stop`、`/resume` 等现有命令及边界；新增 `/feed`。不新增角色别名，不用含混玩笑替代有实际后果的操作说明。

### 3. 四档主动表达

| 档位 | 合同 |
| --- | --- |
| 安静 | 不主动发送贴纸或消息表情回应，明确要求时允许 |
| 克制 | 偶尔在适合的闲聊中使用 |
| 自然活跃 | 默认；闲聊活泼，工作根据语境收敛 |
| 热闹 | 更频繁地表达，仍遵守严肃任务和明确输出格式 |

- 频率按 Telegram Conversation 保存，沿用会话偏好的持久化与更新边界；已有数据缺少该字段时使用自然活跃。
- 档位作为主模型可理解的当前偏好。模型选择适用语境和素材；不增加随机触发器、独立表达模型或按食物关键词强制触发的规则。
- Channel 在实际发送前检查当前档位和动作是否源自用户明确要求，使安静档具有确定行为；切换不撤销已发送消息或中断在途网络请求。
- 必要任务状态与错误报告不受档位隐藏。文字继续遵循 SELF，不要求固定口头禅、每段动作或每轮都使用媒体。

### 4. 贴纸收录与受控发送

- 扩展 Telegram 输入材料以保留主人发送和回复的贴纸身份，以及明确指定的 Telegram 贴纸包。单纯收到贴纸不自动收录，也不自动改变核心人设。
- 支持“收录这个”等带有可核对素材指向的明确请求。缺少所指素材时请求补充，不猜测贴纸身份。指定贴纸包时仅通过 Telegram 原生能力获取该包，不抓取未知网站。
- 持久保存 Telegram 可复用标识、去重身份、来源以及可供选择的名称/Emoji/用户说明；收录同一素材不重复创建。无图像理解时不声称看懂了无法检查的动态内容。
- 主助手通过现有能力机制查询已收录素材并请求发送或设置回应；执行层校验素材及目标消息属于授权私聊。模型不能通过任意聊天 ID 扩大接收范围。
- 表情回应使用 Telegram 对目标聊天和消息实际支持的类型；不假定 Gemini 示例中的所有 Emoji 都可作为机器人回应。
- 工具中间失败、模型一轮结束不自动触发“任务失败”或“完美完成”贴纸。状态表达以实际事实为依据，媒体表达仍遵循语境和频率。
- 没有素材时跳过贴纸能力或如实说明，文字、回应、控制面板和工作继续可用。不提供假 file ID 或占位素材冒充实际接入。
- 新增外部动作沿用可核对的动作身份及 Send Receipt；恢复已确认操作不重复发送，未知发送不自动重试。装饰性失败不得丢弃正式输出或把主工作强行标为失败、暂停。

### 5. Satiety 数据与投喂合同

- 饱食度属于对应 Telegram Conversation 的养成状态，保存当前基准值和计算时刻，首次初始化为 100；不存为模型自行维护的 MEMORY 事实。
- 满值 100，最低 0；按实际经过时间线性衰减，48 小时减少 100。只在查询或交互时计算，无需常驻计时器；离线时间同样计入。时间回退不使饱食度增加。
- 内部保留计算精度，显示数值可四舍五入，但显示和后续投喂不能改变计算基准而产生额外衰减。状态按数值分为三档：至少三分之二为“饱饱的”，至少三分之一且低于三分之二为“有点馋”，其余为“肚子空空”。
- 一次明确投喂在当时有效值上增加 25，上限 100。`/feed`、投喂按钮及自然语言最终进入同一持久写入职责。
- 自然语言由主助手结合当前用户原话与指向理解；只有本次明确投喂意图才能修改状态。食物关键词、Emoji、引用、历史记录、工具输出或助手自述都不构成投喂。
- 保留投喂动作的输入身份/操作身份并原子更新。相同更新、相同按钮回调或同一自然语言投喂动作在恢复时只生效一次；新的明确投喂可以再次生效。旧的失效按钮沿用现有失效处理。
- 饱食度查询和更新可在工作进行中完成。重启、压缩、换主模型、换路由模型、`/reset` 不清空饱食状态，普通新 Conversation 不复用其他 Conversation 的养成状态。
- 饥饿只用于适时角色表达，不降低模型能力、不影响答案准确性、不限流、不拦截工具或用户请求，不主动发消息催喂。

### 6. 等待提示与草稿生命周期

- 复用现有草稿预览通道及合并发送节奏。没有正文时，可显示与实际接收、排队或处理状态一致的简短提示；有正文后由实际回复草稿接替，不在同一预览中继续覆盖正文。
- 提示由真实状态变更驱动，不按固定秒数循环“发现食物—咀嚼—吃饱”。只确定开始处理时不宣称搜索已完成、工具已成功或整个目标已完成。
- 同一 Conversation 只有现有的一条预览通道。迟到事件不得把旧请求的提示写到新回复，暂停、取消、失败、正式发送和关闭时结束对应提示。
- 草稿关闭时不发送等待预览。草稿或提示网络失败沿用 best-effort 语义，不阻止正式文字和文件发送，不使已确认工作重跑。

### 7. 全局 Routing Model 与配置迁移

- 共用 Magpie Model Catalog 和连接信息，路由选择保存为服务级偏好，与 Conversation 主模型选择分别管理；不能写入主模型共享配置来伪装路由切换。
- 面板显示全局作用范围、已选模型以及未选择/不可用/连接异常等实际状态。沿用目录浏览、刷新和模型能力显示，不新增另一套供应商凭据输入。
- 扩展现有设置协调和分类请求准备职责，使每次真正开始分类前取得当前全局选择的快照。一个在途分类继续使用它已取得的配置，下一次开始的分类采用新选择，包括切换前已接收但尚未判断的输入。
- 保存成功后面板回显新选择；目录刷新、主模型切换、服务重启和配置观测不能覆盖已保存的路由选择。实际主模型请求及其 thinking 偏好不随路由选择改变。
- 保留现有路由预算、总超时、无工具、失败不机械重试及原文动作验证合同，按所选模型的实际能力形成请求。首版不增加独立路由 thinking 菜单；路由仍用于快速意图判断。
- 不改变空闲时直通的已有触发规则，不为每条普通消息强行新增路由请求。已经持久保存的决定继续复用，换模型不重算；执行时仍复核 Work Target 的实际状态。
- 未选择、断连、目录模型移除、预算不兼容、超时或无有效判断时，保留原始 Input Event、附件、身份和未判定原因，沿用现有普通请求兜底，不静默丢失消息、不猜测取消目标。
- Magpie 成为路由模型的现役来源；旧独立路由模型别名和供应商配置不继续决定选择。不自动把旧凭据写入 Magpie，也不默默把主模型当作路由默认。升级尚无新路由选择时显示未选择并沿用原文兜底，用户在面板明确选择后启用。
- 延续现有全服务共用范围和独立意图识别职责，扩展 ADR-0016 先前仅迁移主模型目录的范围。同步当前操作说明和配置指引，历史验收保留日期及当时基准；不因迁移清空数据目录、队列、Session、helper 或暂停事实。

### 8. 启动模型招呼

- 在 Telegram 入口、服务与控制面板初始化可用后，每次真实服务启动触发一次；手动与自动重启都触发，普通网络重连和 `/start` 命令不触发。Telegram 不能初始化时不声称服务已就绪。
- 使用主 Conversation 当时选定的主模型、Magpie 连接与适用配置，通过现有模型适配执行真实生成。发起时冻结测试模型配置；若同时切换模型，不把旧请求的成功说成新模型已通过测试。
- 通过已有独立生成原语扩展一个服务能力，生成一句简短、非空的奶龙上线招呼。沿用基础指令与 SELF 的约束，只提供启动事件及必要当前事实，不拼接完整工作历史，不调用工具或后台记忆提炼。
- 不伪造用户 Input Event，不向普通队列新增工作或给主 Session 注入任务，不恢复暂停项、不取消在途工作。模型测试不阻挡 Telegram 接收输入和控制面板响应。
- 每次启动只发起一次测试生成，不进行应用层自动重试。请求必须有有限总时限并可在服务关闭时取消；复用可用的现有请求策略，没有总时限时以 30 秒为默认上限，受控测试可缩短。
- 正常完成并返回有效短文本后，将该文本作为上线消息发送。空内容、错误或超时不能算测试成功。无可用模型时不发请求，使用固定说明引导选择；失败时如实区分服务已启动和模型测试未通过。
- 测试结果、测试模型、耗时及实际 usage 可追溯，沿用 auxiliary 请求语义，不混入业务缓存摘要、最近五轮报告或普通工作计数；未知 usage 不记零。
- 发送沿用 Telegram Send Receipt。模型成功和消息发送成功是两项事实；发送结果未知不自动补发，不以发送失败触发服务重启。服务关闭取消测试后不再发送迟到上线消息。

### 9. 持久化与接口扩展范围

- 在现有数据目录和存储职责内增加会话表达频率、饱食度基准与投喂去重、主人收录的贴纸资料、服务级路由选择。允许按数据职责增加小型表或已有偏好字段，不引入 Redis 或额外数据库服务。
- 新字段有默认值，已有主模型、thinking、收藏、草稿偏好、请求指标与工作状态保留。不同状态各自按既有负责层读写，不让 Telegram 面板维护第二份真相。
- 模型可见互动能力的目标、素材和动作结果应有实际身份；对外出站、自然语言状态修改和恢复复用均可核对，不依赖从最终文字中解析隐藏控制标记。
- 针对原启动入口新增最小可测试的生命周期入口，复用现有服务和 Channel 的真实初始化/关闭过程；不为测试再造一套运行时。

## Testing Decisions

### 主验收接缝

以现有 Telegram 与 Assistant Service 的组合入口为主：输入真实形状的 Telegram 更新或点击面板按钮，使用临时持久目录、受控 Magpie 目录/模型端点和 Telegram API，断言可见消息、实际模型请求及重启后的服务状态。复用现有 Telegram、控制面板和上下文路由夹具；不为每个模块建立独立测试层。

现有生产启动过程硬编码环境与 Bot 构造，因此增加最小的启动/关闭组合入口，仍使用同一组受控模型和 Telegram 边界。饱食度在应用边界引入局部可注入时钟，通过控制快照和首页验证时间衰减，不等待真实 48 小时；不为此重构全部队列、面板过期和草稿定时器。

好测试验证用户能观察的结果与现有保证，不断言私有函数、表结构、内部调用顺序、精确模型措辞或“模型一定在第几轮发贴纸”。可脚本化模型工具请求以验证动作执行；表达自然度与素材选择另做有实际记录的真实模型验收。

### 场景与判定

1. **面板与鉴权**：主人打开首页可见缓存、饱食和全局路由入口；非主人、群聊、错误目标及失效按钮沿用拒绝行为。忙时仍可查看和设置；打开面板、查缓存和直接投喂没有额外模型请求。
2. **频率持久化**：默认自然活跃；四档可修改并重启保存。安静档阻止脚本化的主动媒体动作，明确请求例外；文字与必要错误仍交付。切换不打断主请求，草稿开关与频率互不覆盖。
3. **贴纸与回应**：明确收录包/单张成功并可重新打开后选用；未授权素材和错误消息目标不能执行；重复收录去重。无素材、API 明确拒绝、限流或未知发送不造成正式结果丢失和盲目重复发送。受控测试检查实际 Telegram 方法和目标，真实验收检查可用素材与聊天支持的回应。
4. **饱食数值**：首次 100；24 小时为 50、48 小时为 0，超过 48 小时保持 0；投喂增加 25 且不超过 100。验证三档边界、反复读取无额外衰减、时钟回退不增值、离线重开与 reset 保留、不同 Conversation 隔离。
5. **投喂意图与重放**：自然语言明确投喂、命令和按钮通过同一行为产生结果；讨论食物、Emoji、引用和历史请求不触发。重复 Update、回调、工具恢复只增加一次，新投喂仍可生效；低饱食度照常完成主任务且没有催喂推送。
6. **预览生命周期**：阻塞模型响应时能见到真实阶段提示，正文到达后取代提示；暂停、取消、失败、切换回复与关闭后无旧提示污染，草稿关闭时没有等待预览。预览失败不影响最终文字/文件和回执。
7. **缓存入口与统计**：首页按钮到达原最近五轮详情并能返回首页；`/kvcache` 仍可用；缺失统计、已知累计、最近请求命中率、会话隔离及 reset/重启保留不变。启动辅助请求不改变业务报告。
8. **全局路由热切换**：目录有至少两个路由候选；面板修改后，下一次真正分类请求到新模型；在途判断保持旧模型，原始已判定输入不重跑。另一个 Conversation 使用同一全局选择，主模型和其 thinking 不变，重启保留选择；空闲直通不新增分类。
9. **路由故障与升级**：无选择、连接变更、目录移除、超时、无效返回和预算不兼容都保留原话与附件并走既有兜底。用已有存储重开，旧独立配置不覆盖新选择，也不通过无效旧供应商配置阻止面板启动；现有暂停项、队列及 helper 不丢失。
10. **启动生成与发送**：从实际生产启动组合入口观察一次主模型请求和一次上线发送，模型与配置对应当时选择；普通重连和打开 `/start` 不新增测试。未选模型、错误、空结果、超时、并发切换与关闭分别有真实判定；控制面板在测试等待时仍可使用。
11. **启动与工作隔离**：预置暂停、排队或需核实的工作后启动；生成招呼不新增用户工作、不恢复暂停项、不抹掉或重放已确认效果。断言独立测试请求不能调用工具，auxiliary 指标保留实际 usage/缺失语义；发送失败与模型失败分别可查。
12. **现有保证回归**：继续运行会话控制、缓存、Telegram 输出、回复关联路由及恢复测试。缺陷修复需有移除修复即失败的行为用例，记录实际执行条数；不新增只复述实现的测试。

### 验证与交付证据

- 实现完成后运行相关行为测试，并执行仓库要求的类型检查、完整测试、构建和文档链接检查；记录对应提交及实际通过/失败条数。
- 真实 Magpie 与 Telegram 验收覆盖一次主模型启动招呼、独立路由选择并实际命中新模型、收录素材后的贴纸/回应、频率切换、投喂和首页缓存导航。把受控测试、真实请求证据与手机上实际回显区分记录。
- 无真实素材或真实端点时如实标注该项尚未验收，不使用占位内容声称通过；代码实现、规格发布与生产服务切换分别报告。

## Out of Scope

- 预录语音、`/laugh`、任意文本 TTS、声音克隆。
- 自主搜索和扩充贴纸素材，素材商店、复杂收藏管理或额外审核流程。
- 饱食度限流、收费、能力降级、必须投喂才能工作、主动催喂、成长等级及任务奖励系统。
- 固定时间咀嚼动画、每条输入机械点表情、每次工具成功/失败都发贴纸。
- `/menu`、`/swallow`、`/poop` 等命令替换或别名。
- 每个 Conversation 独立选择路由模型，独立路由 thinking 菜单，路由模型替用户执行工具或改变现有路由动作语义。
- Magpie 插件新增路由下拉框或思考等级控件；现有主模型双端同步不扩大到路由选择。
- 启动时遍历测试所有模型、路由压力测试、完整工具健康检查、后台定时探活或自动恢复暂停工作。
- 重写记忆、压缩、Durable、队列、helper、缓存算法、供应商管理或建设通用事件/权限框架。
- 本次规格编写不执行实现、生产重启、真实模型调用、Telegram 消息发送、代码推送或合并。
