# 输入意图路由讨论

2026-10-16，用户通过 grill-with-docs 重新讨论 Telegram 输入路由。本文件随访谈记录已确认决定与未决问题；整体设计尚未确认，运行代码未修改。最终结论确认后按项目约定发布 GitHub Issue。

## 当前基线与参考

- 基线提交：`95ee5cb`。当前运行规则见 [ADR-0011](../adr/0011-durable-main-agent-and-conversation-queue.md)：直接输入同级 FIFO，普通消息不隐式补充当前工作，仅显式 `/steer` 接入当前工作。连续普通消息合批保留身份与边界，不判断是否属于同一目标。
- [Magpie 意图路由](https://usemagpie.ai/docs/zh/intent)使用小模型读取候选意图和最新消息，再由规则选择回答模型；它不读取之前轮次。此方法可供参考，但本项目要判断消息与已有工作的关系，不能把最新消息分类直接视为完整设计。
- [herdr-workflow](../../.agents/skills/herdr-workflow/SKILL.md)已规定：委派后登记后台观察，主助手结束当前工具轮次；用户插话时，无关交流直接回应，明确的编码补充转交对应帮手，无法判断归属时询问。

## 第一轮已确认

1. **普通消息可补充当前工作。** 结合上下文识别自然语言补充或修改，在下一个可接收输入的边界生效。用户同意移除 `/steer`，认为它是原 coding agent 输入方式的遗留产物。此决定重新打开 ADR-0011 中普通消息不隐式 steering 的约束；当前实现仍保留旧入口。
2. **后台委派释放主 Bot。** 耗时大的工作应交给 herdr helper。已委派的工作在后台运行时，主 Bot 可以立即处理用户新输入；不等待 helper 完成整个目标。主 Bot 自身仍在处理输入时的规则见第二轮结论。
3. **按上下文确定取消目标。** 用户明确指定对象时取消该对象；省略对象但当前只有一项工作时，该工作就是目标；存在多个可能对象且上下文不足以唯一确定时才询问用户。取消后的实际停止仍须依据执行进程和证据确认，沿用现有 herdr 停止规则。

## 第二轮已确认

1. **独立新请求继续 FIFO。** 主 Bot 自身还在生成回复或调用短工具时，无关的新问题等待当前短轮次结束，按到达顺序处理；相关补充在下一个可接收输入的边界接入。耗时工作交给 helper，避免主 Bot 长时间占用当前轮次。
2. **取消尽快中断对应执行。** 目标明确的取消请求尽快发起中断，不等待补充输入边界或整项工作完成。对 helper 核对实际进程及停止证据，确认停止后再报告结果，保留已有成果。此决定也要求后续设计区分“已请求中断”和“已确认停止”。

## 第三轮已确认

1. **独立模型负责初判。** 使用独立的快速模型识别新消息的意图与目标，程序按已确认的规则路由，主 Bot 负责详细理解和对应执行。模型需要读取新消息、近期对话及相关工作的有限摘要；上下文方案见第四轮，失败时的交接见第六轮。
2. **排队请求的修改保留原位置。** 对尚未开始的请求，后续修改关联到原请求并保留其 FIFO 位置；开始执行时使用合并后的要求。明确取消则撤销对应待办，不先执行旧版本再返工。

## 第四轮已确认

1. **采用有限对话上下文与实际工作列表。** 判断输入包含当前消息及其 Telegram 回复关系、近期几轮用户与 Bot 的对话，以及正在处理、排队和后台 helper 工作的身份、简短目标和实际状态。复用现有事件、批次及 helper 记录生成工作列表；不以完整历史、工具输出或全部文件作为每次分类的默认输入。
2. **输出动作和目标。** 快速模型表达当前消息与哪项工作的关系，由程序按前几轮规则路由；不能仅返回适合哪种回答模型的类别。动作包括独立请求、补充、取消或需要澄清。具体轮数、长度预算、模型选择与超时数值留给规格阶段。

## 第五轮已确认

1. **复合消息保留多个动作。** “报表别做了，帮我查天气”拆为两个关联动作：尽快发起取消报表，天气查询按 FIFO 排队。不要求用户拆成两条消息，也不等待确认报表完全停止后才接收新请求。
2. **helper 补充及时转交。** 主 Bot 正在处理另一件事时，目标明确的后台 helper 补充及时转交，不被无关问题挡住。保留原消息及投递状态，发送成功与 helper 已采纳分别确认。

## 第六轮已确认

1. **原输入通过普通队列兜底。** 分类超时、报错或需要视觉理解时，复用原始 Input Event 及普通会话队列：保留事件身份、用户原文、回复关系与图片附件，按原接收顺序进入下一次普通处理，不复制为新消息、不伪造用户指令，也不把未判定输入自动注入当前工作。
2. **附带独立的运行时路由说明。** 主 Bot 领取输入时，另外获得关联原事件的“未判定”状态及超时、错误或需要视觉理解等原因；说明与用户正文分开，不包含模型臆测的目标，并明确尚未针对任何工作执行补充或取消。原消息仍以用户身份进入，同一个主 Bot 结合正常上下文和最新工作状态决定处理或澄清，不额外启动 agent。
3. **保持普通处理时机与媒体内容。** 空闲时立即开始这一轮，忙碌时等待当前短轮次释放。必须看图才能理解时，原图随原消息交给支持视觉的主 Bot，不要求用户重新打字。

## 待最终核对的保证与实现约束

- 执行动作前核对目标的实际状态。判断期间工作已结束时，补充转为基于现有成果的后续修改；取消也不能假定执行仍在进行。
- 分类失败不能被报告为已取消或已补充；无法及时执行停止请求时明确告知用户当前尚未停止。
- 继承现有持久队列与 Durable Workflow 的身份、去重和恢复保证。路由决定及投递进度须与原始输入关联，重启按已记录的进度核对，不丢输入、不盲目重派 helper，也不凭未知发送结果重复投递。

## 未决分支

- 独立目标是否仍允许共用输入批次；合批怎样保留各项目标与补充关系。
- 最终核对上述保证与实现约束，并确认完整设计形成共同理解；模型、预算、超时和恢复协议的具体实现留到正式规格。
