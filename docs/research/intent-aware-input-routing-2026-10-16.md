# 输入意图路由讨论

2026-10-16，用户通过 grill-with-docs 重新讨论 Telegram 输入路由。本文件随访谈记录已确认决定与未决问题；整体设计尚未确认，运行代码未修改。最终结论确认后按项目约定发布 GitHub Issue。

## 当前基线与参考

- 基线提交：`95ee5cb`。当前运行规则见 [ADR-0011](../adr/0011-durable-main-agent-and-conversation-queue.md)：直接输入同级 FIFO，普通消息不隐式补充当前工作，仅显式 `/steer` 接入当前工作。连续普通消息合批保留身份与边界，不判断是否属于同一目标。
- [Magpie 意图路由](https://usemagpie.ai/docs/zh/intent)使用小模型读取候选意图和最新消息，再由规则选择回答模型；它不读取之前轮次。此方法可供参考，但本项目要判断消息与已有工作的关系，不能把最新消息分类直接视为完整设计。
- [herdr-workflow](../../.agents/skills/herdr-workflow/SKILL.md)已规定：委派后登记后台观察，主助手结束当前工具轮次；用户插话时，无关交流直接回应，明确的编码补充转交对应帮手，无法判断归属时询问。

## 第一轮已确认

1. **普通消息可补充当前工作。** 结合上下文识别自然语言补充或修改，在下一个可接收输入的边界生效。用户同意移除 `/steer`，认为它是原 coding agent 输入方式的遗留产物。此决定重新打开 ADR-0011 中普通消息不隐式 steering 的约束；当前实现仍保留旧入口。
2. **后台委派释放主 Bot。** 耗时大的工作应交给 herdr helper。已委派的工作在后台运行时，主 Bot 可以立即处理用户新输入；不等待 helper 完成整个目标。主 Bot 自身仍在处理输入时的规则见第二轮结论。
3. **按上下文确定取消目标。** 用户明确指定对象时取消该对象；省略对象但当前只有一项工作时，该工作就是目标；存在多个可能对象且上下文不足以唯一确定时才询问用户。取消后的实际停止仍须依据执行进程和证据确认，沿用现有 herdr 停止规则。

## 第二轮已确认

1. **独立新请求继续 FIFO。** 主 Bot 自身还在生成回复或调用短工具时，无关的新问题等待当前短轮次结束，按到达顺序处理；相关补充在下一个可接收输入的边界接入。耗时工作交给 helper，避免主 Bot 长时间占用当前轮次。
2. **取消尽快中断对应执行。** 目标明确的取消请求尽快发起中断，不等待补充输入边界或整项工作完成。对 helper 核对实际进程及停止证据，确认停止后再报告结果，保留已有成果。此决定也要求后续设计区分“已请求中断”和“已确认停止”。

## 第三轮已确认

1. **独立模型负责初判。** 使用独立的快速模型识别新消息的意图与目标，主 Bot 按结果执行路由和动作。模型需要读取新消息、近期对话及相关工作的有限摘要；具体上下文边界和失败策略仍待确认。
2. **排队请求的修改保留原位置。** 对尚未开始的请求，后续修改关联到原请求并保留其 FIFO 位置；开始执行时使用合并后的要求。明确取消则撤销对应待办，不先执行旧版本再返工。

## 未决分支

- 意图判断需要读取哪些上下文；判断失败、超时或结果不确定时如何降级。
- 图片、文件或只有媒体没有文字的输入是否交给同一判断模型，还是直接按消息类型路由。
- 一条消息同时包含多个目标时，是拆成多个待办、保持一个批次，还是要求用户拆分。
- 对应 helper 的补充如何及时送达，以及发送与消费状态如何确认。
- 已排队输入如何处理相关补充、独立目标与取消；原 FIFO 与合批规则哪些仍适用。
- 路由与执行状态变化相遇、服务重启时如何保留原输入和已作决定。

后续只对用户确认的分支补充结论；候选方案不作为已接受约束。术语见 [CONTEXT](../../CONTEXT.md)。
