# 事件队列与主 agent 持久工作流规格草稿

Based on #200

日期：2026-10-15。状态：已确认行为的规格整理，待用户整体核对后发布独立规格 Issue。本文件中标为“拟定”的实现细节与验收边界尚待本次核对；不是运行时已具备的能力。

## Problem Statement

长期运行的个人助手需要可靠接收输入，按会话和优先级协调工作。当前原生 Session 会保存历史，但输入先只记录去重身份，进程崩溃后可能丢失已接收而未完成的工作。普通新输入自动 steering 的行为也不符合用户确认的同级 FIFO。仅保存会话或待办，无法恢复主 agent 的模型与工具步骤；外部效果不明时从头重跑可能重复操作。

## Solution

nailong 自有持久队列负责外部事件接收、路由、去重、会话选择、优先级与合批，Pi Durable 1.2.0 承载主 agent 的持久执行。普通消息同级 FIFO，在轮次结束或空闲时读取已排队的有限连续快照，不主动等待时间窗。Telegram 显式 `/steer` 才补充当前工作。高优先级可抢占低优先级后台轮次，之后根据最新指令判断继续、调整或结束。进程重启自动恢复意外中断，已确认成果复用；明确暂停的工作保留暂停状态。

## User Stories

1. 作为用户，我希望已确认接收的消息在重启后仍可处理，以便不必重新交办。
2. 作为用户，我希望同一来源消息重复投递不重复执行，以便通道重试不会产生重复动作。
3. 作为用户，我希望各会话的输入和结果各自归属正确，以便不会串入别的会话。
4. 作为用户，我希望同优先级消息按顺序处理，以便后来的普通输入不会擅自改动当前轮次。
5. 作为用户，我希望直接输入优先于后台事件，以便能改变后台工作的方向。
6. 作为用户，我希望被抢占的工作保留已确认结果，以便不重复已完成操作。
7. 作为用户，我希望续接前核对最新要求，以便作废的旧计划不会机械继续。
8. 作为用户，我希望已排队的连续普通消息可一起交给下一轮，以便减少重复启动。
9. 作为用户，我希望系统不为凑批等待固定时间窗，以便能立即处理已有输入。
10. 作为用户，我希望每条合批消息保留身份和边界，以便不同事项不会被默认为同一目标。
11. 作为用户，我希望用 `/steer 内容` 明确补充当前工作，以便普通排队输入与运行中补充有清晰区别。
12. 作为用户，我希望连续补充可按序一起读取，以便不遗漏也不重复注入。
13. 作为用户，我希望空闲时 `/steer` 的正文仍能正常入队，以便补充不会无声丢失。
14. 作为用户，我希望主 agent 派发 herdr 后可处理后续输入，以便不等待帮手整个目标结束。
15. 作为用户，我希望帮手返回摘要和证据位置，以便主会话不会被所有执行细节占满。
16. 作为用户，我希望重启后查询原帮手身份并接回成果，以便不盲目重新派发。
17. 作为用户，我希望主 agent 检查实际成果，以便状态或自报不能冒充验收。
18. 作为用户，我希望模型和工具的已确认结果可以恢复，以便服务中断不会使工作从头再来。
19. 作为用户，我希望临时网络故障有限重试，以便短暂故障无需每次人工处理。
20. 作为用户，我希望重试耗尽后保留进度并暂停通知，以便自己决定何时继续。
21. 作为用户，我希望一项工作暂停后仍可处理其他输入，以便故障不会堵住整个会话。
22. 作为用户，我希望工具或业务错误交给主 agent 判断，以便不机械重复无效操作。
23. 作为用户，我希望外部效果不明时先核实，以便不会重复发送、提交或修改。
24. 作为用户，我希望无法核实的操作暂停询问，以便自己决定下一步。
25. 作为用户，我希望 `/reset` 只清主上下文而保留事件、进度与委派，以便重置不等于取消工作。
26. 作为用户，我希望继续使用现有模型配置、技能、项目指令和在用工具，以便迁移后能力不中断。
27. 作为用户，我希望 Telegram 图片、文件、草稿与发送回执继续工作，以便成果仍能正常使用。
28. 作为用户，我希望 CLI 继续支持明确选择会话，以便本地工作流可以接入。
29. 作为用户，我希望切换时从空白会话开始、不迁移旧历史，以便新运行时不携带旧对话内容。

## Implementation Decisions

### 已确认的责任与行为

- 维持 Channel、Assistant Service 与主 agent 的分工：Channel 鉴权并收发；队列系统持久接收、路由和调度；Durable 保存模型/工具执行事实。采用新的执行持久化，不恢复已退役 Host 的通用 Task/Attempt、结算或权限协议。
- 输入确认接收前，将来源、源消息身份、会话、正文、图片恢复材料和入队顺序一起持久提交；不能只保存 ID。相同正文但不同源消息 ID 是不同输入。
- 同会话只运行一个主 agent 处理轮次。完成轮次不表示用户整个目标或外部帮手已经完成。不同会话可以分别推进，不能让一个全局执行等待阻塞其他会话的接收。
- 普通同级输入 FIFO；直接用户输入高于后台来源。高优先级可抢占低优先级，保留已确认成果，之后结合新要求核对继续、调整或结束。
- 当前轮结束或空闲时固定一个有限队列快照，只取同会话、同来源、同优先级的连续普通前缀；命令与来源/优先级变化是屏障。不主动等待窗口，不跨屏障收集后面的项。快照后到达的新消息进入后续轮次。
- 合批保留各原始事件身份、正文、材料和顺序，不把消息合为一个不可追溯的新源事件，也不判断它们必定属于同一业务目标。
- 只有 Telegram 显式 `/steer` 才提交为运行中补充；剥离前缀但保存原事件和控制身份。连续补充可在下一个支持的输入边界一起读取，普通输入不混入 steer。空闲时正文转普通输入，遵守已有队列顺序；空命令显示用法。
- `steer` 不等于立刻中止模型或工具，也不替代优先级抢占。Durable 的工具轮边界可将补充加入原 run；若模型已最终答复，则补充可能进入后续 run。不能承诺所有补充都在原 run 消费。
- 普通等待事件留在应用队列，不提前全部放进 Durable inbox。当前选定批次和显式 steer 与 Durable submission 保留稳定关联；恢复先核对已提交事实，避免成功提交后应用尚未记录而盲目重交。
- 临时模型/基础设施故障有限重试；模型请求只由执行器一层负责，不叠加底层重试，也不通过重跑整轮来重试单次请求。工具/业务错误交回模型判断，任意 Shell 不一概标 safe。
- 重试耗尽保留进度、暂停该项并通知一次，等待明确继续；其他输入照常推进。重启保留主动暂停或待用户核实状态，不能误当作意外中断自动续跑。
- 外部效果不明时先核实：确认完成则采用结果，确认未执行才执行，无法核实则暂停询问。打断、重置或取消都不回滚已发生效果。工作完成与通道发送回执是不同事实，未知 Telegram 发送不自动重发。
- 主 agent 派发 herdr 后可结束本轮；保存目标与真实 session/agent/workspace/pane/cwd/prompt 身份。重启查询原执行，不盲重派。帮手返回内部摘要和证据位置，不混入普通用户队列、不因回传本身直接发 Telegram；主 agent 核查实际成果。
- `/reset` 重置主上下文，保留已接收事件、进度和帮手；继续时加载必要工作材料。明确取消另按实际目标、工具或帮手身份处理，不能将 reset 当成取消。
- 保留现有模型身份、端点、兼容配置、推理设置、项目指令/技能、MCP 与其他在用工具、`herdr_watch`、`send_file`、图片、草稿和回执；替代后删除旧注册实现，不建设无使用者的通用旧扩展兼容层。已有 `/help`、`/model` 继续可用，控制操作不能丢弃排队输入。
- 新会话从空白开始，不导入旧会话历史、摘要或详细工具轨迹。不把旧历史伪造成 Durable 完成回执；旧外部委派按真实身份核对，不因旧对话不加载就盲目重新派发。

### 拟定的具体实现细节，随本草稿整体核对

- Telegram 沿用既有私人会话身份和 `message_id`，去重键包含来源、会话与源消息 ID；CLI 沿用会话选择与一次输入 UUID。CLI 用户再次执行 send 生成新身份，不声称跨独立调用自动去重。
- 普通同级事件合成一个处理批次，批次固定成员与执行关联。主 agent 结束处理轮次后原子记录成员已被本轮处理；这不是逐个业务目标已完成的声明。回复可统一组织，但模型仍能看到各条消息边界。重启恢复原批次，不能把半批消息重新作为新输入执行。
- 临时模型故障沿用 Durable 的默认策略：最多重试 3 次，即含首次最多 4 次请求，基础等待 2 秒；底层 provider 重试关闭。重试计数跟随同一次执行恢复，不因重启或改投新 submission 而绕过上限。对存在未知外部效果的工具不套用模型请求的重试策略。
- herdr 返回先持久保存，在当前轮结束后交付给主 agent；已排队的直接用户输入先处理。内部结果与用户输入共用同会话串行协调，内部回执去重，但不伪装用户消息，也不进入外部输入队列。
- 使用独立的新执行数据空间，保留现有配置和凭据接入；切换不删除旧目录或成果文件。迁移命令/启动检查区分新旧空间，不能因复用配置目录而意外加载旧会话。

## Testing Decisions

拟沿用现有 Assistant Service 的输入接收、输出订阅、等待空闲及重开数据目录，作为主要验收边界。使用受控模型与工具观察实际输入、调用次数、成果和输出，不绑定私有方法或 SQL 表名。通道层沿用现有 Telegram 假服务器及 CLI 集成方式；跨进程恢复使用独立子进程，强杀后重开同一存储，验证实际效果与原始身份，不只检查日志文案。

| 场景 | 必须观察到的行为 |
| --- | --- |
| 接收、去重与材料 | 接收确认后强杀仍保留正文、图片恢复材料与顺序；重复源消息只处理一次；同正文不同身份各自处理 |
| 会话隔离与串行 | 同会话不并发两个主轮次，其他会话可接收并推进；结果回到所属会话 |
| 普通合批 | A 执行时 B/C 排队；A 后下一轮按序可见 B/C；快照后 D 不混进该批；命令/来源/优先级屏障不跨越 |
| 显式补充 | 仅 `/steer` 在边界加入；连续补充身份与顺序保留；覆盖工具中到达、最终答复时到达、空闲、空命令 |
| 调度与续接 | 直接输入抢占后台；同级普通输入不抢占；旧工作在新指令下分别继续、调整、结束；确认成果不重复 |
| 崩溃交接 | 接收、领取、提交、保存 submission、模型/工具完成、队列完成确认前后分别强杀；恢复不丢输入，不盲目重交，不重做已确认操作 |
| steer 与 abort | 持久补充在中断/抢占后核对已消费状态，不能丢失，也不能同时进入当前和后续轮次两次 |
| 重试与暂停 | 短暂请求故障有限重试；不重跑整个轮次、不叠加底层重试；耗尽后保留进度、通知一次、其他输入可处理；重启不绕过暂停 |
| 工具恢复与效果核实 | 已确认结果复用；safe 工具恢复按幂等约定，unsafe 未决操作先核实；完成/未执行/无法核实三种结果各有明确处理 |
| reset | 清理上下文后事件、进度和委派仍存在；必要材料可重新加载，完整旧上下文不被自动放回 |
| herdr | 派发后释放主轮次，重启接回原身份、内部结果只交付一次；状态不代替实际成果验收 |
| 模型与通道 | 现有模型配置、指令/技能、MCP/在用工具、图片、文件、草稿、鉴权、未知发送回执和 CLI 选择会话继续工作 |
| 切换 | 新主会话不含旧历史；真实旧委派先核对，不因切换新存储盲目重派；旧目录未被迁移流程删除 |

现有 runtime、交互、herdr 和 Telegram 测试是回归先例；其中“普通输入自动 steering”的旧断言必须按已确认新行为替换，不能为了通过旧测试保留错误调度。已有 9 项独立实验是接入证据，不替代正式入口验收；外部项目测试源码也不计入本项目通过数。

## Out of Scope

cron、邮件、群聊、Slack 连接器；herdr 内部逐工具持久恢复；完整分层记忆、Akasha 重启用与缓存优化；通用旧扩展兼容层；旧 Host 协议恢复；跨系统 exactly-once 与已发生外部效果的回滚；服务器部署、多 bot；旧会话历史转换及本地旧数据物理清理。
