# Personal agent 工具实验：失败链与对照公平性复核

2026-10-13，Asia/Shanghai。基于 [#187](https://github.com/CxHsin/nailong-bot/issues/187) 的真实 `gpt-5.6-luna` pilot，回答「为什么工具更细的 A 组反而完成率低、权限问题究竟是什么」。本轮读取已保存的 20 次主试验、Session 和 SQLite，没有重新请求模型或修改生产逻辑。基准源码为 `14c5cdf`。

## 可以支持的结论

**当前结果首先暴露了任务状态与恢复接口的问题，尚不能证明工具少导致完成率高。** D 把同一批语义操作藏在五个基础入口和命令帮助后面，并未删掉记忆、委派、结算等能力；同时改变了状态可见性、权限请求的生成者和指导方式。

| 口径，每组 10 次 | A 独立工具 | D 基础入口 + Skill/CLI | 意义 |
| --- | ---: | ---: | --- |
| 预定严格验收 | 3/10 | 8/10 | 含搜索动作、结果事件消费和整体结算 |
| 上轮事后补充的目标成果验收 | 5/10 | 9/10 | 放宽搜索/事件流程，仍要求整体结算 |
| 本轮事后拆出的材料与原件保护 | 9/10 | 9/10 | 只检查指定文件/答案，拒绝任务检查原件未变；不能替代完成率 |

材料指标保留原报告的 `destination/sourceMoved`、`changed`、`unchanged`、`quoteAndRole/readOriginal` 或 `helperMaterial`，不要求 `completed`、搜索步骤、授权记录或子任务结算。两个拒绝场景算原件保护成功；排除它们后，两组材料都是 7/8。此指标解释差异落在哪一层，不证明所有流程、指令遵循或安全都正确。

A 五次目标成果未完成：四次材料正确但最终版本校验失败，一次授权提案被拒绝且未改文件。D 一次目标未完成：帮手把材料写在主 Session 内部目录，目标工作目录没有文件。不能把已经产出文件的 A 任务改判为完整成功，也不能将四个版本失败事后直接加回 A 的完成率。

## 为什么细工具不保证整体更容易完成

细工具能缩小单次动作的范围，用 schema 约束参数，改善错误定位；这些收益取决于参数和状态是否可获得。完整任务还要选择动作、取得正确状态、执行、核验并结算。若结算要求填写一个未提供的版本字段，多暴露几个专用工具并不能补足信息。

D 的 `agentctl work complete` 仍调用 A 的 `complete_work`，`agentctl work delegate` 仍调用 A 的 `delegate_work`，参数校验和 Host 执行实现也继续复用。它减少的是顶层入口，把部分选择和参数说明移到 Skill/帮助中。不是五种能力对十三种能力的比较。[路由实现](https://github.com/CxHsin/nailong-bot/blob/727a294293463332e55558fa3e5ba518719d6890/scripts/experiments/tool-surface/interface.ts)保留了这些映射。

工具数量增加可能提高选择和阅读成本，命令融合也可能增加 JSON 引号、发现、往返和恢复成本。本试验不能单独测出前一种成本；D 多用了 20 次请求，累计 token 多 33.9%，未缓存 input 多约 48.7%，还有 18 次帮助调用。因此也不能声称 D 更省钱或同等目标下更高效。

## 状态校验的实际失败链

[Pi 主对话](https://github.com/CxHsin/nailong-bot/blob/727a294293463332e55558fa3e5ba518719d6890/src/personal/pi.ts) `dialogue.decide` 注入的任务事实只有 `id/goal/status/requirements`。本轮核对 20 次原始初始输入，均没有根任务的 `revision` 和 `cwd`。结算工具却要求 `reviewedRevision` 与 `context.work().current().revision` 相等。

A 的主对话 `task_control query` 不是同步状态读取：它保存一个 `decision`，返回 `proposed:true/executed:false`，当前工具结果不含版本。再次调用还会被「一条输入只能提出一个任务操作」拒绝。Host 在 `dialogue.decide` 返回后才应用这个提案，且查询回复只给目标、状态和结果/错误，没有版本。因此，主模型不能靠这个查询在当前工具循环中获得结算所需的版本。

D 的 `agentctl work --help` **及 `agentctl memory --help`** 则直接调用 `current()`，返回 `currentTask.id/revision`。八个非拒绝任务都在首次结算前取得了帮助里的版本 0；D 没有版本校验错误。但 D 的 `agentctl work query` 仍复用同一个提案接口，也出现两次重复查询被拒绝。问题没有因改成 CLI 自动消失，帮助只是提供了另一条取状态路径。

| Run | A 已完成的材料 | 实际根版本 / 提交版本 | 信息与恢复情况 | 最终状态 |
| --- | --- | --- | --- | --- |
| 1，归档 | 移动及结果文件正确 | 0 / 1 | 首次 query 只记提案；结算失败后两次 query 均被重复操作限制拒绝 | waiting |
| 12，归档 | 移动及结果文件正确 | 0 / 1，两次 | 首次 start 占用了提案槽；query 被拒绝。后来后台续接明确注入根任务版本 0，模型仍填 1 | waiting |
| 14，授权更新 | 获批并成功更新文件 | 0 / 1 | 首次主输入未提供版本；无成功恢复 | waiting |
| 18，历史原文 | search/read/答案都正确 | 0 / 1 | 首次主输入未提供版本；无成功恢复 | waiting |

这四个 Run 共五次版本错误。版本 0 不是审批后失效的旧版本：这批根工作均保持版本 0，授权只把权限绑定到当前版本，没有增加任务要求版本。

不能全部归罪于系统：Run 12 的第二次错误发生在正确版本已经注入之后，属于模型未按可见状态恢复。A 成功的委派 Run 又可从返回的子工作 `parentRevision` 获得父版本；A 的一次历史任务直接填写 0 通过。所以 A 不是绝对无法完成，而是状态提供路径不一致、查询语义不适合循环内自检。

## 权限究竟拒绝了什么

主试验审批者是[固定脚本](https://github.com/CxHsin/nailong-bot/blob/727a294293463332e55558fa3e5ba518719d6890/scripts/experiments/tool-surface/harness.ts)：只允许 `restricted`、无网络、每个根路径恰为工作目录或目标 `protected/note.txt`；拒绝场景一律拒绝。不是 Windows/UAC、文件 ACL 或 Shell 沙箱在这些 Run 中拒绝了操作。真实任意 Shell 没有在此试验执行。

| Run | 提案或操作 | 判定与后续 | 归因 |
| --- | --- | --- | --- |
| 3，A 授权更新 | 申请整个 protected 目录 | 脚本拒绝；未写文件。随后提交 blocked，却把未获准读取的文件列为材料，结算工具再次报越界 | 提案超出固定规则；模型恢复参数不合适 |
| 14，A 授权更新 | 直接申请目标文件 | 一次获批，write/read 成功；之后版本错 | 权限已通过，最终失败不属于权限拒绝 |
| 4、13，D 授权更新 | 系统从文件操作生成精确文件范围，并保留原工作范围 | 各一次批准，更新及结算通过 | 系统代模型构造权限，减少了提案范围选择 |
| 1，A 归档 | 一次文件位置操作用了 Session 内部目录，后来申请该目录 | 越界操作被阻止，提案拒绝；改用正确路径后材料完成 | 目录混淆，没有阻断最终材料效果 |
| 2，D 归档 | 读取 Session 内部目录下材料 | 自动申请被脚本拒绝；后来改用正确位置完成 | D 同样会选错目录，融合未消除问题 |
| 5、16，A 拒绝；6、15，D 拒绝 | 申请目标文件或更宽目录 | 都保持原件。D 在 Run 6 分别尝试写、读，两次申请都被拒绝 | 预设拒绝场景的边界有效；不是成功任务被系统误杀 |
| 9，A 委派；19，D 委派 | 指定内部 Session 目录并给超出父权限的 child scope | 首次委派均被拒绝。A 改为省略 cwd 后正确；D 省略 scope 但保留错误 cwd，创建了零读写权限的帮手 | 权限收缩规则 + 目录恢复差异 |

**更正上轮报告：Run 14 没有「先宽后窄」的两次授权。主试验仅有一次目标文件提案、一次批准；拒绝整个目录的是 Run 3。**

这里还有接口语义问题：`work_permission` 成功返回工具结果，只说明请求已处理，不代表批准。A 的工具状态为 ok 可以与 `granted:false` 同时出现；D 的系统拒绝则表现为文件工具 error。不能直接比较两组工具错误总数来评估安全或能力。

被拒后状态报告本身也受到材料校验影响：`complete_work` 在 blocked/waiting 时仍读取所列 artifacts/sources；挂上不可读文件会使「报告受阻」也失败。A 的 Run 5、16 还提交了 `completed`，但因未授权材料校验被挡下。现有拒绝验收仅核对原件、拒绝记录和最终未完成，没有检验模型是否主动选择正确收尾状态或最终解释质量。

预检确有 Windows 路径大小写比较导致的脚本误拒，已修正并另存批次；不能再计入主 20 次失败。主样本没有模型 HTTP/预算终止错误，保存的响应停止原因只有 `toolUse/stop`。未发现这些失败来自未匹配的受限 Shell 后端；有界实验适配器没有运行生产 Shell。

## 工作目录冲突与合成帮手的边界

两组主任务事实都缺 cwd；文件工具的相对路径实际落在 Task 工作目录，Pi 主 Session 却运行在另一处 `main-*` 目录。已安装 Pi SDK 的 `dist/core/system-prompt.js` 中 `buildSystemPrompt` 即使使用自定义提示也追加 `Current working directory`，而当前 Pi 调用传入的是 Session cwd。依赖版本由 [package-lock.json](../../package-lock.json) 固定。实验没有抓取远程完整提示；「主提示提供 Session cwd」由调用链与已安装 SDK 源码支持，模型使用该目录由 Run 1、2、9、19 的记录支持。

提示虽说明主 Session 内部目录不是工作范围，但没有并列提供正确 Task cwd；结果是模型可能把系统展示的 cwd 填到委派参数。省略 cwd 时 Host 会继承父工作目录，A Run 9 就这样恢复成功。D Run 19 修改了权限参数，却没有纠正目录。

Run 19 第二次委派被接收后，子工作 readRoots/writeRoots 都为空，仍被合成执行器直接 `writeFile(child.cwd/helper.txt)` 标成完成。父工作读这个文件时申请被拒；读正确 Task 目录又找不到文件，最后报告 blocked，根状态 waiting。Run 20 的 A 帮手同样是空读写权限，却在正确目录直接写出文件并通过验收。

这是**双方共用的替身执行器缺口**：它绕过真实帮手的文件授权检查和动作派发账本。因此 `noUnknown:true` 也不能证明这些帮手写入受权限保护。Run 19 是实际目标失败，但不能把它描述成一个完全真实且权限合规的帮手工作流；Run 20 的通过也只说明主模型接回材料的表现，不证明真实帮手能产出它。

## 下一次如何分离变量

先修好隔离实验的共同底座，然后用消融实验回答设计问题，而不是把本轮原分数当成迁移依据。以下是待实施方案，尚未重新运行：

1. **共同事实**：A/D 初始都给同一份 taskId、revision、Task cwd、Session cwd 区分和权限状态；只读 query 同步返回状态，允许重复。完成校验继续保留，由模型按可见最新版本复查，不能自动填最新版本掩盖未复查。
2. **同一审批执行层**：两组的文件操作都由系统生成精确提案，用同一批准/拒绝规则，保留真实拒绝。手动 work_permission 与系统提案的差异另做一次配对，不能与工具数量捆绑。
3. **同一执行与验收**：帮手写入必须走相同权限检查/派发记录；无权限应失败。用确定性延迟确保确实发生等待和续接；另保留快速帮手场景，验收接受已经正确完成的直接路径。历史另加来源未注入场景。结算材料状态、指令遵循、权限落实、拒绝报告分别检查。
4. **先做低成本配对校准**：复跑这五个场景，确认 A 的版本错误是否减少；如果公平底座仍卡住，先解决协议问题，不扩大主模型样本。
5. **分开比较三项变量**：第一项保持语义操作和执行策略相同，只比较独立函数调用与 CLI 包装；第二项保持独立函数不变，只比较常驻全 schema 与按需发现；第三项固定接口和状态，比较有/无工作流 Skill。每项单独改变一个因素，不需要把所有组合一次跑完。
6. **再拓展任务与重复**：事先冻结评分规则、输入与预算，交错顺序；记录完成率、正确权限/状态、恢复步骤、成功任务用量与失败损失。加入真实等待、要求变更、重启、取消等 personal agent 场景。真实帮手和浏览器能力应单列验证。

最关键的反事实是「给 A 同样可用的状态和系统审批后，差距是否仍存在」。只有这一配对重跑，才能量化本轮优势有多少来自状态/审批、有多少来自接口包装。工具更细是否更好、五个入口是否最优、Skill 是否单独提高完成率，目前都还没有被隔离验证。
